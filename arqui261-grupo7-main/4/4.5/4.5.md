# 4.5. Módulo 5 / Integrante 5

# ADR-01: Asignación de Responsabilidades para Reseñas y Reputación

## Título

Separación de responsabilidades entre gestión de reseñas, reputación e historial.

## Contexto

El módulo M5 tiene como objetivo incrementar la confianza entre propietarios y arrendatarios dentro de DriveShare. Para ello debe permitir registrar reseñas, almacenar comentarios, consultar historial, visualizar reputaciones y actualizar automáticamente la puntuación de los usuarios.

Los requisitos RF39 al RF48 establecen diversas responsabilidades que podrían concentrarse en un único componente o distribuirse en varios servicios.

## Alternativas

### Alternativa 1

Implementar toda la funcionalidad en un único componente de reseñas.

### Alternativa 2

Separar las responsabilidades en componentes especializados:

* Gestión de reseñas.
* Gestión de reputación.
* Historial de evaluaciones.
* Moderación y reporte de comentarios.

## Criterios de Elección

* Mantenibilidad.
* Escalabilidad.
* Cohesión.
* Facilidad de pruebas.

## Decisión

Se selecciona la Alternativa 2.

## Sustento

La separación de responsabilidades permite que cada componente tenga una función específica. Esto facilita futuras modificaciones, como agregar nuevos criterios de reputación o mecanismos de moderación sin afectar el resto del módulo.

# ADR-02: Modelo de Coordinación basado en APIs REST

## Título

Integración síncrona entre Reseñas, Usuarios y Reservas.

## Contexto

Antes de registrar una reseña es necesario validar que:

* El usuario se encuentre autenticado (RF44).
* La reserva exista.
* La reserva haya finalizado correctamente (RF45).

Por ello el módulo debe comunicarse con los módulos de Usuarios y Reservas.

## Alternativas

### Alternativa 1

Comunicación síncrona mediante APIs REST.

### Alternativa 2

Comunicación asíncrona mediante colas de mensajes.

### Alternativa 3

Modelo híbrido REST + eventos.

## Criterios de Elección

* Simplicidad.
* Tiempo de respuesta.
* Facilidad de implementación.
* Consistencia de validaciones.

## Decisión

Utilizar comunicación síncrona mediante APIs REST.

## Sustento

Las validaciones de autenticación y estado de reserva deben realizarse en tiempo real antes de aceptar una reseña. REST permite obtener respuestas inmediatas y simplifica la integración entre módulos.

# ADR-03: Modelo de Datos Relacional para Reputación y Reseñas

## Título

Persistencia de reseñas y reputaciones mediante PostgreSQL.

## Contexto

Las reseñas deben estar asociadas a usuarios y reservas específicas. Asimismo, el sistema debe garantizar la trazabilidad de comentarios, calificaciones e historial de reputación.

## Alternativas

### Alternativa 1

Base de datos relacional PostgreSQL.

### Alternativa 2

Base de datos documental MongoDB.

### Alternativa 3

Modelo híbrido.

## Criterios de Elección

* Integridad referencial.
* Consistencia de datos.
* Facilidad para consultas históricas.
* Soporte transaccional.

## Decisión

Utilizar PostgreSQL.

## Sustento

La relación entre usuarios, reservas y reseñas requiere integridad referencial. PostgreSQL garantiza consistencia transaccional y facilita consultas sobre reputación, historial y evaluaciones realizadas.

# ADR-04: Gestión de Recursos mediante Caché de Reputación

## Título

Optimización de consultas frecuentes de reputación.

## Contexto

Uno de los requisitos funcionales más importantes del módulo es permitir que los usuarios consulten reputaciones y reseñas de otros usuarios (RF42 y RF43).

Estas consultas pueden realizarse continuamente durante la búsqueda de vehículos y evaluación de propietarios.

## Alternativas

### Alternativa 1

Calcular la reputación en cada consulta.

### Alternativa 2

Mantener reputaciones precalculadas y almacenadas.

### Alternativa 3

Utilizar caché para reputaciones frecuentemente consultadas.

## Criterios de Elección

* Rendimiento.
* Escalabilidad.
* Consumo de recursos.
* Experiencia de usuario.

## Decisión

Utilizar almacenamiento de reputaciones calculadas y caché para consultas frecuentes.

## Sustento

Esta decisión permite cumplir el escenario de rendimiento definido para el módulo, manteniendo tiempos de respuesta inferiores a tres segundos incluso bajo alta concurrencia.

# ADR-05: Elección de Tecnología

## Título

Uso de NestJS, PostgreSQL y Redis para el módulo de Reseñas y Reputación.

## Contexto

El módulo debe integrarse con la arquitectura general de DriveShare y soportar requisitos de seguridad, disponibilidad y rendimiento.

## Alternativas

### Alternativa 1

NestJS + PostgreSQL + Redis.

### Alternativa 2

Express + MongoDB.

### Alternativa 3

Spring Boot + PostgreSQL.

## Criterios de Elección

* Modularidad.
* Rendimiento.
* Compatibilidad con el proyecto.
* Facilidad de mantenimiento.

## Decisión

Seleccionar NestJS como framework backend, PostgreSQL como base de datos principal y Redis como mecanismo de caché.

## Sustento

NestJS proporciona una arquitectura modular alineada con los principios de mantenibilidad. PostgreSQL asegura la integridad de las relaciones entre usuarios, reservas y reseñas. Redis permite optimizar consultas de reputación y mejorar el rendimiento general del sistema.
