# 4.1. Módulo 1 / Integrante 1

# Decisión 1 (Asignación de Responsabilidades)

## Título

Elección entre arquitectura monolítica modular y microservicios para el módulo de Usuarios

## Contexto

El módulo de Usuarios debe permitir el registro, autenticación y administración de perfiles dentro de la plataforma DriveShare. Además, debe gestionar información sensible como credenciales, datos personales y mecanismos de acceso al sistema.

Debido a que este módulo concentra funciones relacionadas con la seguridad de la plataforma, es necesario garantizar una adecuada protección de contraseñas, una gestión segura de secretos y un almacenamiento confiable de la información de los usuarios. Si estos aspectos no se gestionan de manera adecuada, el módulo puede volverse más difícil de mantener y aumentar los riesgos asociados a la seguridad de la aplicación.

La necesidad principal es contar con una solución que permita proteger la información sensible de los usuarios y administrar los secretos de forma segura, manteniendo al mismo tiempo una implementación que pueda evolucionar junto con las necesidades de la plataforma.

## Alternativas

| Alternativa                   | Descripción                                                                                                                                      | Ventajas                                                                                                                | Desventajas                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Monolito modular              | El sistema se implementa como una única aplicación, organizada internamente en módulos y componentes con responsabilidades claramente definidas. | Menor complejidad operativa, mejor organización del código, facilidad de mantenimiento y evolución gradual del sistema. | Escalabilidad menos flexible que los microservicios, ya que el despliegue se realiza de manera conjunta. |
| Microservicios independientes | Cada funcionalidad se implementa como un servicio independiente con despliegue y ejecución separados.                                            | Alta escalabilidad independiente, flexibilidad tecnológica y despliegues desacoplados.                                  | Mayor complejidad en infraestructura, monitoreo, comunicación entre servicios y mantenimiento.           |

## Criterios de Elección

* Cohesión del sistema.
* Complejidad de la arquitectura.
* Ordenamiento del código.
* Separación de responsabilidades.
* Mantenibilidad del sistema.

## Decisión

Se decide implementar una arquitectura monolítica modular para el módulo de Usuarios, organizando el backend en componentes con responsabilidades claramente definidas.

## Sustento

Se adopta una arquitectura monolítica modular debido a que proporciona una adecuada separación de responsabilidades sin introducir la complejidad operativa asociada a los microservicios. Esta alternativa facilita la organización del código, mejora la mantenibilidad y permite gestionar de manera más eficiente los aspectos relacionados con la seguridad del módulo, como la protección de credenciales, la administración de secretos y el almacenamiento de información sensible. Asimismo, ofrece una base sólida para la evolución futura de la plataforma, manteniendo un equilibrio entre simplicidad arquitectónica y capacidad de crecimiento.


# Decisión 2(Modelo de Coordinación)

## Título: 
Elección de Modelo de coordinación síncrono mediante API REST

## Contexto

El módulo debe gestionar el registro de usuarios, autenticación, recuperación de contraseñas, administración de perfiles y control de acceso.

La mayoría de estas operaciones requieren una respuesta inmediata para el usuario, ya que forman parte de procesos interactivos como el inicio de sesión, el registro y la recuperación de contraseña.

Por ello, el modelo de coordinación debe priorizar simplicidad, compatibilidad e integración con otros componentes de la plataforma.

## Alternativas

| Alternativa | Descripción | Ventajas | Desventajas |
|------------|------------|------------|------------|
| Modelo síncrono | El cliente espera una respuesta inmediata del servidor para cada solicitud. | Fácil implementación y respuesta inmediata para el usuario. | Dependencia directa entre cliente y servidor, lo que puede afectar la escalabilidad en ciertos escenarios. |
| Modelo asíncrono | Las solicitudes se procesan en segundo plano y el resultado se obtiene posteriormente. | Mejora la escalabilidad y reduce bloqueos en el sistema. | Mayor complejidad en la gestión de procesos y estados. |
| Modelo híbrido | Combina operaciones síncronas y asíncronas según el tipo de proceso. | Flexibilidad para distintos escenarios de uso. | Requiere definir claramente qué procesos utilizan cada mecanismo, aumentando la complejidad del diseño. |

## Criterios de Elección

- Necesidad de respuesta inmediata.
- Complejidad de implementación.
- Mantenibilidad del sistema.
- Facilidad de integración con otros componentes del sistema.


## Decisión

Se decide utilizar un modelo de coordinación síncrono mediante API REST.

## Sustento

Esta decisión se fundamenta en la necesidad de obtener respuestas inmediatas en los procesos principales del sistema, como autenticación, registro de usuarios, recuperación de contraseñas y consulta de perfiles.

Dicho enfoque nos permite mantener una implementación simple y directa, donde el cliente realiza una solicitud y recibe una respuesta en tiempo real, lo que reduce la complejidad del flujo de comunicación.

Además, el uso de API REST facilita la integración con otros componentes del sistema, incluyendo servicios externos y el frontend, manteniendo un diseño consistente y ampliamente compatible.

# Decisión 3 (Modelo de Datos)

## Título:
Eleccion de Modelo Relacional PostgreSQL

## Contexto

El módulo debe almacenar información de usuarios, perfiles y contraseñas protegidas.

Estos datos presentan relaciones bien definidas y requieren consistencia para garantizar una correcta identificación, autenticación y control de acceso dentro de la plataforma.

## Alternativas

| Alternativa | Descripción | Ventajas | Desventajas |
|------------|------------|------------|------------|
| Modelo relacional | Los datos se organizan en tablas con relaciones estructuradas entre entidades. | Garantiza integridad de datos, soporte para transacciones y consultas estructuradas. | Requiere diseño adecuado de esquemas y relaciones. |
| Modelo documental | Los datos se almacenan en documentos con estructura flexible. | Alta flexibilidad para cambios en la estructura de datos. | Dificulta la gestión de relaciones complejas entre entidades. |
| Modelo híbrido | Combina almacenamiento relacional y documental según el tipo de información. | Permite flexibilidad y especialización según el caso de uso. | Mayor complejidad en el diseño y mantenimiento del sistema. |

## Criterios de Elección

- Integridad de los datos.
- Consistencia en la información.
- Facilidad de consultas estructuradas.
- Mantenibilidad del sistema.

## Decisión

Se decide utilizar un modelo relacional implementado con PostgreSQL .

## Sustento

Esta decisión se basa en la necesidad de garantizar consistencia e integridad en la información de usuarios, así como la correcta gestión de relaciones entre entidades dentro del sistema.

El modelo relacional permite aplicar restricciones de integridad, realizar consultas estructuradas y mantener una organización clara de los datos.


# Decisión 4 (Gestión de Recursos)

## Título:

Decisión de Rate Limiting para el control de solicitudes en el módulo de usuarios

## Contexto

El módulo de usuarios expone operaciones críticas como registro, autenticación y recuperación de contraseña.

Estas operaciones pueden ser objetivo de múltiples solicitudes simultáneas o abusivas, lo que puede afectar el rendimiento del sistema y la estabilidad del servicio.

Por ello, es necesario establecer un mecanismo que permita controlar la cantidad de solicitudes realizadas al sistema en un periodo de tiempo determinado.

## Alternativas

| Alternativa | Descripción | Ventajas | Desventajas |
|------------|------------|------------|------------|
| Sin control de solicitudes | El sistema procesa todas las solicitudes sin restricciones ni límites. | Implementación simple y directa. | Riesgo de saturación del servidor y posible abuso del sistema. |
| Rate limiting | Se aplican límites al número de solicitudes que un usuario puede realizar en un periodo de tiempo. | Protege el sistema ante abuso, mejora la estabilidad y evita sobrecarga. | Puede afectar a usuarios legítimos si no se configuran adecuadamente los límites. |
| Pool de conexiones con control de carga y paginación | El sistema reutiliza las conexiones a la base de datos en vez de abrir una nueva cada vez, también controla cuántas consultas se hacen al mismo tiempo y limita la cantidad de datos que se traen en cada consulta. | Hace que el sistema sea más rápido y no se sobrecargue cuando hay muchas solicitudes. | Requiere una buena configuración para que no se sature o se vuelva lento si no se ajusta bien. |

## Criterios de Elección
- Protección del sistema ante abuso de solicitudes.
- Estabilidad del servicio bajo alta carga.
- Sencillez de implementación.

## Decisión

Se decide implementar rate limiting como mecanismo de control de solicitudes en el módulo de usuarios.

## Sustento

Esta decisión permite limitar el número de solicitudes que un usuario puede realizar en un periodo de tiempo, reduciendo el riesgo de abuso o ataques de fuerza bruta en endpoints críticos como autenticación y registro.


# Decisión 5 (Mapeo entre Elementos de Arquitectura)

## Título:

Elección de Mapeo por capas entre elementos de arquitectura

## Contexto

El sistema debe estructurarse de forma que la interfaz de usuario, la lógica de negocio y el acceso a datos se encuentren claramente diferenciados.

Esta separación permite organizar mejor el sistema, facilitando su mantenimiento, pruebas y evolución a futuro.

## Alternativas

| Alternativa | Descripción | Ventajas | Desventajas |
|------------|------------|------------|------------|
| Mapeo Directo | Todos los componentes del sistema se desarrollan sin separación clara entre interfaz, lógica y persistencia. | Menor tiempo de desarrollo inicial y simplicidad en sistemas pequeños. | Genera acoplamiento entre componentes y dificulta el mantenimiento a largo plazo. |
| Mapeo por capas | La arquitectura se organiza en niveles donde cada uno cumple una función específica dentro del sistema. | Mejora la organización del código, facilita el mantenimiento y reduce dependencias entre componentes. | Requiere planificación previa para definir correctamente cada capa. |
| Mapeo distribuido mediante microservicios | El sistema se divide en servicios independientes según funcionalidades del dominio. | Permite escalabilidad y despliegue independiente de cada servicio. | Incrementa significativamente la complejidad de desarrollo, despliegue y comunicación. |

## Criterios de Elección

- Separación de responsabilidades.
- Ordenamiento de la arquitectura.
- Complejidad del sistema.
- Mantenibilidad del código.
- Facilidad de pruebas.

## Decisión

Se decide utilizar un mapeo por capas para estructurar los elementos de arquitectura del sistema.

## Sustento

Esta decisión se fundamenta en la necesidad de mantener una separación clara entre la interfaz de usuario, la lógica de negocio y el acceso a datos.

El enfoque por capas permite organizar el sistema de manera estructurada, reduciendo el acoplamiento entre componentes y facilitando el mantenimiento, las pruebas y la evolución del sistema.

Se descarta el uso de microservicios debido a la complejidad adicional que introduce en el desarrollo y la infraestructura, la cual no es necesaria para el alcance del proyecto.


# Decisión 6 (Elección de Tecnología) 
## Titulo: PostgreSQL + HashiCorp Vault + RSA-2048 OAEP SHA-256 + bcrypt

## Contexto
El módulo de Usuarios es una de las piezas centrales de la plataforma DriveShare, ya que se encarga de gestionar el registro, autenticación, administración de perfiles y control de acceso de los usuarios del sistema.

Dado que maneja información sensible como datos personales y contraseñas, es fundamental garantizar la seguridad de los datos, la autenticación segura de los usuarios y la correcta gestión de secretos del sistema.


## Alternativas evaluadas

| Alternativa | Descripción | Ventajas | Desventajas |
|------------|------------|------------|------------|
| PostgreSQL + HashiCorp Vault + RSA-2048 + bcrypt | Solución enfocada en la protección de credenciales, gestión segura de secretos y cifrado asimétrico. | Alto nivel de seguridad, gestión centralizada de secretos y protección robusta de contraseñas. | Mayor complejidad de configuración y administración de infraestructura. |
| PostgreSQL + AWS Secrets Manager + AES-256 + Argon2 | Alternativa basada en servicios administrados con cifrado simétrico y protección avanzada de contraseñas | Menor carga operativa, alta seguridad y fácil integración con servicios en la nube. | Dependencia de proveedor externo y posibles costos asociados |
| MySQL + Autenticación Local + Variables de Entorno (.env) | Solución sencilla con almacenamiento local de configuraciones y autenticación propia de la aplicación. | Fácil implementación, menor complejidad y rápida puesta en marcha. | Menor nivel de seguridad y escalabilidad en comparación con gestores especializados de secretos |

## Criterios de elección

- Protección de datos sensibles
- Facilidad para crecer junto con la plataforma.
- Facilidad de administración, actualización y monitoreo 
- Complejidad de implementación

## Decisión

Se selecciona la alternativa **PostgreSQL + HashiCorp Vault + RSA-2048 OAEP SHA-256 + bcrypt** para el módulo de Usuarios de DriveShare.

## Sustento

La alternativa elegida ofrece el mejor equilibrio entre seguridad y control de la información sensible. PostgreSQL proporciona un sistema de gestión de bases de datos robusto y confiable para almacenar la información de los usuarios. HashiCorp Vault permite centralizar y proteger los secretos de la aplicación, reduciendo el riesgo de exposición de credenciales.

Por otro lado, bcrypt proporciona un mecanismo seguro para el almacenamiento de contraseñas mediante hashing, mientras que RSA-2048 permite implementar cifrado asimétrico para proteger información sensible y facilitar el intercambio seguro de datos cuando sea necesario.
