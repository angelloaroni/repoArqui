# 4.3. Módulo 3 / Rodrigo Figueroa

# ADR-01: Asignación de Responsabilidades del módulo de Reservas

## Contexto

El módulo de Reservas es el núcleo operativo de DriveShare. Su responsabilidad principal es coordinar el proceso de alquiler entre propietarios y arrendatarios desde que se solicita una reserva hasta que el vehículo es devuelto.

Durante este proceso se deben validar fechas disponibles, gestionar cambios de estado, controlar cancelaciones, registrar devoluciones y mantener sincronizada la información con los módulos de Vehículos, Pagos y Notificaciones.

Debido a que cada una de estas actividades responde a reglas de negocio diferentes, es necesario definir claramente cómo se distribuyen las responsabilidades dentro del módulo.

## Alternativas evaluadas

| Alternativa | Descripción | Ventajas | Desventajas |
|------------|------------|------------|------------|
| Gestión centralizada | Un único componente controla disponibilidad, estados, historial y devoluciones. | Diseño inicial sencillo. | Dificulta la evolución del módulo. |
| Responsabilidades orientadas al flujo de reserva | Cada componente se enfoca en una etapa del ciclo de vida de la reserva. | Facilita mantenimiento y trazabilidad. | Requiere mayor diseño inicial. |
| Microservicios especializados | Cada etapa opera como un servicio independiente. | Escalabilidad independiente. | Mayor complejidad de despliegue. |

## Decisión

Se decide organizar las responsabilidades alrededor del ciclo de vida de la reserva.

La arquitectura distinguirá claramente componentes encargados de la validación de disponibilidad, gestión de estados, historial de reservas y cierre de alquileres.

Esta distribución permite reflejar directamente el proceso de negocio y facilita futuras ampliaciones del módulo.

# ADR-02: Modelo de Coordinación para el Proceso de Reservas

## Contexto

El módulo de Reservas coordina múltiples actividades durante el proceso de alquiler de un vehículo. Cuando un arrendatario realiza una solicitud, el sistema debe verificar la disponibilidad del vehículo, registrar la reserva, gestionar su estado y coordinarse con el módulo de Pagos para completar la confirmación.

Asimismo, una vez producidos cambios importantes como confirmaciones, modificaciones o cancelaciones, los usuarios involucrados deben ser informados oportunamente.

Debido a que algunas operaciones son críticas para la experiencia del usuario y otras pueden ejecutarse posteriormente, es necesario definir un mecanismo de coordinación adecuado entre los componentes del sistema.

## Alternativas evaluadas

| Alternativa | Descripción | Ventajas | Desventajas |
|------------|------------|------------|------------|
| Modelo completamente síncrono | Todas las validaciones, pagos y notificaciones se ejecutan durante la misma solicitud. | Flujo sencillo y fácil de comprender. | Aumenta los tiempos de respuesta y la dependencia entre módulos. |
| Modelo completamente asíncrono | Todas las operaciones se procesan mediante eventos en segundo plano. | Mayor desacoplamiento y escalabilidad. | El usuario no obtiene confirmaciones inmediatas. |
| Modelo híbrido | Las operaciones críticas se ejecutan de forma síncrona y las complementarias de forma asíncrona. | Equilibrio entre rapidez de respuesta y escalabilidad. | Requiere identificar claramente cada flujo. |

## Decisión

Se decide utilizar un modelo híbrido para coordinar el proceso de reservas.

Las operaciones relacionadas con la validación de disponibilidad, creación de reservas, modificaciones y cancelaciones se ejecutarán de forma síncrona para proporcionar una respuesta inmediata al usuario.

Por otro lado, las notificaciones de confirmación, cancelación, recordatorios de inicio y actualizaciones de historial se ejecutarán de forma asíncrona.

Esta decisión permite mantener una experiencia de usuario fluida sin comprometer la escalabilidad del sistema ni aumentar innecesariamente el tiempo de respuesta de las operaciones principales.

# ADR-03: Modelo de Datos para la Gestión de Reservas

## Contexto

El módulo de Reservas administra información relacionada con solicitudes de alquiler, períodos reservados, estados de reserva, modificaciones, cancelaciones y devoluciones de vehículos.

Además, debe mantener relaciones consistentes con los usuarios que participan en la reserva y con los vehículos involucrados, garantizando que no existan conflictos de disponibilidad durante un mismo intervalo de tiempo.

Debido a que las reservas representan operaciones críticas para el negocio, es necesario seleccionar un modelo de datos que permita mantener integridad, trazabilidad y consistencia en toda la información gestionada por el módulo.

## Alternativas evaluadas

| Alternativa | Descripción | Ventajas | Desventajas |
|------------|------------|------------|------------|
| Modelo relacional | La información se organiza mediante tablas relacionadas para reservas, usuarios, vehículos y estados. | Permite integridad referencial y soporte para transacciones. | Requiere definir adecuadamente las relaciones entre entidades. |
| Modelo documental | Cada reserva se almacena como un documento independiente. | Mayor flexibilidad para cambios en la estructura de datos. | Dificulta el manejo de relaciones complejas y restricciones de integridad. |
| Modelo híbrido | Combina almacenamiento relacional para reservas y documental para historiales o registros secundarios. | Flexibilidad y especialización según el tipo de información. | Incrementa la complejidad de administración y sincronización. |

## Decisión

Se decide utilizar un modelo de datos relacional para gestionar la información del módulo de Reservas.

Las entidades principales estarán asociadas a reservas, vehículos, usuarios, estados de reserva e historial de operaciones. Las relaciones entre estas entidades permitirán controlar la disponibilidad de los vehículos, registrar cambios de estado y mantener un seguimiento completo del ciclo de vida de cada reserva.

Esta alternativa proporciona la consistencia necesaria para evitar conflictos de disponibilidad, facilita la implementación de reglas de negocio y garantiza la integridad de la información almacenada.

# ADR-04: Mapeo entre Elementos de Arquitectura del módulo de Reservas

## Contexto

El módulo de Reservas debe gestionar procesos relacionados con la búsqueda de disponibilidad, creación de reservas, modificaciones, cancelaciones, consulta de historial y cierre de alquileres.

Además, necesita interactuar con otros módulos de la plataforma como Usuarios, Vehículos, Pagos y Notificaciones, manteniendo una separación adecuada entre la interfaz de usuario, las reglas de negocio y el acceso a los datos.

Una organización inadecuada de estos elementos puede generar dependencias innecesarias, dificultar el mantenimiento y aumentar el impacto de futuras modificaciones.

## Alternativas evaluadas

| Alternativa | Descripción | Ventajas | Desventajas |
|------------|------------|------------|------------|
| Mapeo acoplado | La interfaz de usuario accede directamente a la lógica y a los datos. | Menor complejidad inicial. | Alto acoplamiento y dificultad para realizar cambios. |
| Mapeo por capas | Se separan claramente las responsabilidades entre presentación, lógica de negocio y persistencia. | Facilita el mantenimiento, las pruebas y la evolución del sistema. | Requiere definir correctamente las responsabilidades de cada capa. |
| Mapeo orientado a servicios independientes | Cada funcionalidad principal opera como un servicio separado. | Mayor flexibilidad y escalabilidad. | Incrementa la complejidad arquitectónica. |

## Decisión

Se decide utilizar un mapeo por capas para organizar los elementos arquitectónicos del módulo de Reservas.

La arquitectura estará compuesta por:

- Capa de Presentación, encargada de la interacción con propietarios y arrendatarios.
- Capa de Aplicación, responsable de coordinar las operaciones relacionadas con reservas.
- Capa de Dominio, donde se implementan las reglas de negocio asociadas a disponibilidad, estados y políticas de cancelación.
- Capa de Persistencia, encargada del almacenamiento y recuperación de datos.
- Capa de Integración, utilizada para comunicarse con los módulos de Pagos, Vehículos y Notificaciones.

Esta estructura permite reducir el acoplamiento entre componentes, facilitar el mantenimiento del sistema y simplificar futuras ampliaciones del módulo.

# ADR-05: Elección de Tecnologías para el módulo de Reservas

## Contexto

El módulo de Reservas constituye el núcleo operativo de DriveShare, ya que coordina la interacción entre propietarios y arrendatarios durante todo el proceso de alquiler de un vehículo.

Este módulo debe permitir consultar disponibilidad, crear reservas, gestionar modificaciones y cancelaciones, mantener el historial de operaciones y coordinarse con los módulos de Vehículos, Pagos y Notificaciones.

La tecnología seleccionada debe garantizar una experiencia fluida para los usuarios, soportar múltiples reservas concurrentes y mantener la consistencia de la información relacionada con disponibilidad y estados de reserva.

## Alternativas evaluadas

| Alternativa | Descripción | Ventajas | Desventajas |
|------------|------------|------------|------------|
| React + Express + PostgreSQL + Docker | Solución basada completamente en JavaScript para frontend y backend. | Facilidad de desarrollo e integración. | Menor rendimiento en operaciones concurrentes. |
| React + FastAPI + PostgreSQL + Redis + Docker | Frontend React, backend FastAPI, base de datos relacional y almacenamiento temporal para disponibilidad. | Alto rendimiento, soporte asíncrono y mejor manejo de concurrencia. | Requiere administrar tecnologías adicionales. |
| Angular + Spring Boot + PostgreSQL + Docker | Solución empresarial basada en Java para aplicaciones de gran escala. | Robustez y estabilidad. | Mayor complejidad y curva de aprendizaje. |

## Decisión

Se decide implementar el módulo utilizando React para la interfaz de usuario, FastAPI para los servicios backend, PostgreSQL como sistema de persistencia principal, Redis para la gestión temporal de disponibilidad y Docker para la contenerización de la solución.

Esta combinación tecnológica permite responder adecuadamente a los requisitos funcionales del módulo y a los atributos de calidad priorizados.

- React permitirá construir interfaces dinámicas para la búsqueda, creación y seguimiento de reservas.

- FastAPI facilitará la implementación de servicios REST de alto rendimiento para la gestión del ciclo de vida de las reservas.

- PostgreSQL garantizará la integridad de los datos relacionados con usuarios, vehículos, reservas y estados.

- Redis permitirá optimizar consultas frecuentes y gestionar información temporal asociada a la disponibilidad de vehículos.

- Docker facilitará el despliegue uniforme de la plataforma en diferentes entornos.

La alternativa seleccionada proporciona un equilibrio adecuado entre rendimiento, disponibilidad, mantenibilidad y escalabilidad, permitiendo que el módulo de Reservas soporte el crecimiento futuro de DriveShare sin comprometer la experiencia de los usuarios.
