# 4.4. Módulo 4 / Integrante 4

## **Módulo de pagos**

### Decisión 1 (Asignación de Responsabilidades)
- **Título**: Elección entre microservicio independiente y monolito modular.
- **Contexto**: El módulo de pagos gestiona el cobro al arrendatario, la retención de fondos durante el periodo de alquiler y la liberación al arrendador al finalizar, además de los reembolsos por cancelaciones. DriveShare opera como intermediario entre particulares, por lo que los errores en pagos afectan la confianza de los usuarios y la viabilidad del negocio. Se necesita determinar si este módulo formará parte de una aplicación unificada o funcionará como un servicio independiente.

- **Alternativas**: 
    1. **Monolito modular:** El módulo de pagos se integra dentro de la aplicación principal, compartiendo base de datos y ciclo de despliegue con Reservas, Usuarios y Catálogo. Menor complejidad operativa inicial, pero un fallo en pagos puede comprometer el resto del sistema.
    
    2.  **Microservicio independiente:** El módulo de pagos se desarrolla y despliega de forma autónoma, con su propia base de datos y API. Permite escalar, actualizar y asegurar el servicio de forma independiente al resto de módulos.

- **Criterios de Elección**: 
    - Aislar fallos para que un error en el módulo de pagos no afecte la disponibilidad de los demás módulos.
    - Los datos financieros requieren controles de acceso distintos al resto de la plataforma.
    - Escalabilidad del módulo de forma independiente ante picos de transacciones. 
- **Decisión**: Microservicio independiente.
- **Sustento**: Un microservicio aísla fallos del módulo de pagos, protege los datos financieros y permite escalarlo de forma independiente.

### Decisión 2 (Modelo de Coordinación)
- **Título**: Elección entre Comunicación híbrida entre el módulo de pagos y otros módulos: REST síncrono para validaciones y mensajería asíncrona para eventos de estado.
- **Contexto**: El módulo de pagos debe coordinarse con el módulo de Reservas (confirmar que el pago fue procesado antes de activar una reserva) y con el módulo de Usuarios (validar identidad antes de ejecutar una transacción). Algunas interacciones requieren respuesta inmediata y otras pueden manejarse con consistencia eventual. Además, se integra con proveedores externos de pagos, cuya disponibilidad no siempre está garantizada.

- **Alternativas**:  
    1. **REST API síncrona:** Toda la coordinación se realiza mediante llamadas HTTP directas.

    2. **Mensajería asíncrona con colas (RabbitMQ):** Los módulos publican y consumen eventos en colas.

    3. **Enfoque híbrido:** REST síncrono para verificaciones críticas y mensajería asíncrona para eventos de estado.

- **Criterios de Elección**:
    - Respuesta inmediata para validaciones críticas.
    - Tolerancia a fallos ante caídas temporales del módulo de pagos.
    - Consistencia eventual para eventos de estado.
    - Mejor manejo de carga en picos de demanda.
- **Decisión**: Enfoque híbrido: REST síncrono para validaciones inmediatas y RabbitMQ para eventos de estado.
- **Sustento**: Las validaciones previas se manejan de forma síncrona porque requieren respuesta inmediata, mientras que los cambios de estado se publican de forma asíncrona para no afectar la experiencia del usuario. Así se equilibran latencia, tolerancia a fallos y throughput.

### Decisión 3 (Modelo de Datos)
- **Título**: Elección entre un modelo de datos relacional vs no relacional.
- **Contexto**: Se necesita almacenar transacciones con trazabilidad completa: cobros, retenciones, liberaciones y reembolsos. Cada transacción debe vincularse a una reserva y a usuarios específicos. 

- **Alternativas**: 
    1. **Base de Datos Relacional (PostgreSQL):** Modelo con tablas relacionadas (transacciones, métodos de pago, historial de estados). Integridad referencial garantizada por claves foráneas y transacciones ACID.

    2. **Base de Datos No Relacional (NoSQL):** Cada transacción se almacena como documento JSON embebido. Flexible para estructuras de datos que pueden variar por proveedor de pago.

- **Criterios de Elección**:
    - Integridad referencial entre transacciones, reservas y usuarios.
    - Soporte ACID para operaciones atómicas de cobro, retención y liberación.
    - Precisión exacta en montos monetarios.
    - Auditoría eficiente del historial de estados y respuestas del proveedor.
- **Decisión**: Se elige una base de datos relacional con PostgreSQL.
- **Sustento**: PostgreSQL es la mejor opción para este caso por su soporte ACID, montos exactos con NUMERIC y auditoría con JSONB.

### Decisión 4 (Gestión de Recursos)
- **Título**: Estrategia para el procesamiento de operaciones de pago ante fallos del proveedor externo.
- **Contexto**: El módulo de pagos depende de un proveedor externo para procesar los cobros. Este proveedor puede experimentar caídas temporales o límites de tasa de solicitudes. En picos de demanda, múltiples operaciones pueden competir por el mismo recurso. Se debe definir cómo gestionar este recurso compartido para evitar que su saturación colapse el sistema.

- **Alternativas**:  
    1. **Procesamiento síncrono con reintentos inmediatos:** Cada operación se ejecuta en tiempo real y se reintenta de inmediato ante un fallo. Simple de implementar, pero puede saturar el proveedor externo y bloquear los hilos del servidor durante timeouts prolongados.

    2. **Lista de espera con reintentos automáticos:** En lugar de procesar el pago de inmediato, el sistema lo guarda en una lista de espera. Un proceso interno va tomando los pagos de esa lista y los envía al proveedor uno por uno. Si el proveedor falla, espera un momento y lo vuelve a intentar automáticamente, sin que el usuario tenga que hacer nada.

- **Criterios de Elección**:  
    - Capacidad de mantener el sistema operativo aunque el tercero falle.
    - Minimizar tiempos de espera muertos.
    - Asegurar que ninguna transacción se pierda si el proveedor falla temporalmente.
- **Decisión**: Cola de trabajos con BullMQ sobre Redis y circuit breaker con Opossum.
- **Sustento**: La cola de trabajos ordena los pagos sin bloquear el servidor y, junto con los reintentos y el circuit breaker, evita perder operaciones ante fallos del proveedor.

### Decisión 5 (Elección de Tecnología)
- **Título**: Elección entre NestJS con TypeScript y FastAPI.
- **Contexto**: El módulo de pagos es un microservicio backend que expone APIs REST, procesa eventos de una cola y se integra con proveedores externos. Se necesita definir el stack considerando compatibilidad con el equipo, familiaridad, soporte externo, uso de recursos y requisitos financieros.
- **Alternativas**: 
    1. **Node.js con NestJS (TypeScript):** Framework modular con inyección de dependencias, integración con TypeORM y BullMQ, y uso de proveedor de pagos mediante el patrón Adapter.
    2. **Python con FastAPI:** Buen rendimiento asíncrono, pero implica un stack distinto al del resto del equipo.

- **Criterios de Elección**: 
    - Compatibilidad con las herramientas y el pipeline del equipo.
    - Familiaridad con NestJS y TypeScript.
    - Soporte oficial para TypeORM y BullMQ.
    - Buen uso de recursos para integraciones con latencia variable.
    - PostgreSQL ofrece mayor solidez para datos financieros que MySQL/MariaDB.
- **Decisión**: Node.js con NestJS (TypeScript) + PostgreSQL + TypeORM + BullMQ + Redis.
- **Sustento**: NestJS con TypeScript reduce errores en la lógica financiera y permite una arquitectura modular. PostgreSQL aporta ACID, NUMERIC y JSONB, TypeORM simplifica el esquema, y BullMQ con Redis cubre la cola de trabajos. Además, el stack es consistente con el resto del equipo.
