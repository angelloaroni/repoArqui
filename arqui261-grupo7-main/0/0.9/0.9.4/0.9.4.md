# 0.9.4. Integrante 4

# **Arquitectura Hexagonal:**

## Desarrollo Conceptual


### 1. Definición

La Arquitectura Hexagonal, también conocida como **Ports & Adapters**, fue propuesta por Alistair Cockburn en 2005. Surge como respuesta a un problema recurrente en el diseño de software: la lógica de negocio (el dominio) termina acoplada a detalles de infraestructura (bases de datos, frameworks web, proveedores externos) dificultando su prueba, mantenimiento y evolución.

La idea central es simple: **el núcleo de la aplicación no debe saber nada sobre el mundo exterior**. No debe conocer si los datos vienen de una API REST, una cola de mensajes o una interfaz de línea de comandos; tampoco debe saber si se persiste en una base de datos relacional, en un archivo o en memoria. El dominio expone y consume únicamente **interfaces abstractas**, y son piezas externas las que se conectan a esas interfaces.

El nombre "hexagonal" no tiene un significado técnico especial, el hexágono es solo una forma conveniente para dibujar un núcleo con múltiples lados, cada uno representando un punto de conexión con el exterior. Podría dibujarse como un círculo o un cuadrado sin cambiar el concepto.

### 2. Problema que Resuelve

Cuando la lógica de negocio se mezcla con detalles de infraestructura (controladores HTTP, ORMs, SDKs de terceros), aparecen tres problemas:

- **Difícil de probar**: probar la lógica de negocio requiere levantar infraestructura real (BD, servicios externos) o crear mocks complejos.
- **Rígida ante el cambio**: cambiar de proveedor externo o de motor de base de datos implica tocar el corazón del sistema, con alto riesgo de introducir errores.
- **Poco reusable**: la misma lógica de negocio no puede reutilizarse fácilmente en otro contexto (por ejemplo, exponerla vía CLI además de vía API REST).

La Arquitectura Hexagonal resuelve esto invirtiendo la dirección de las dependencias: **la infraestructura depende del dominio, nunca al revés**.

### 3. Conceptos Clave

#### 3.1 El Núcleo (Domain / Application Core)

Es el centro del hexágono. Contiene:

- **Entidades y reglas de negocio**: los objetos y las reglas que representan el problema que el software resuelve, independientemente de cómo se use o se almacene esa información.
- **Casos de uso (Application Services)**: orquestan las reglas de negocio para cumplir una tarea específica (por ejemplo, "procesar el cobro de una reserva").

El núcleo no importa ni depende de ninguna librería de infraestructura, framework web, ni driver de base de datos.

#### 3.2 Puertos (Ports)

Un **puerto** es una interfaz definida por el núcleo que describe una capacidad que el núcleo necesita o que el núcleo ofrece. Existen dos tipos:

- **Puertos de entrada (Driving/Primary Ports)**: definen cómo el mundo exterior puede invocar al núcleo. Por ejemplo, una interfaz `ProcesarPagoUseCase` con un método `ejecutar(datos)`.
- **Puertos de salida (Driven/Secondary Ports)**: definen qué necesita el núcleo del mundo exterior, sin decir cómo se implementa. Por ejemplo, una interfaz `PasarelaDePagoPort` con métodos `cobrar()` y `reembolsar()`, sin mencionar ningún proveedor específico.

Los puertos son **contratos abstractos**, no implementaciones. Pertenecen al núcleo.

#### 3.3 Adaptadores (Adapters)

Un **adaptador** es una implementación concreta de un puerto, que traduce entre el lenguaje del núcleo y el lenguaje de una tecnología o servicio externo específico. También existen dos tipos, simétricos a los puertos:

- **Adaptadores de entrada (Driving/Primary Adapters)**: traducen una solicitud externa (HTTP, un mensaje de cola, un comando CLI) en una llamada al puerto de entrada del núcleo. Ejemplo: un controlador REST que recibe una petición HTTP y llama al caso de uso correspondiente.
- **Adaptadores de salida (Driven/Secondary Adapters)**: implementan un puerto de salida conectándose a una tecnología concreta. Ejemplo: una implementación de `PasarelaDePagoPort` que se comunica con un proveedor de pagos específico.

Cada adaptador vive **fuera** del núcleo y depende de él (nunca al revés).

#### 3.4 Simetría de la Arquitectura

Una idea clave de Cockburn es que, desde la perspectiva del núcleo, **no hay diferencia arquitectónica entre un usuario humano, un sistema externo automatizado o una prueba automatizada**: todos entran a través de un puerto de entrada mediante un adaptador. Esto significa que sustituir la interfaz de usuario por una suite de pruebas automatizadas, o sustituir una base de datos real por una en memoria, es simplemente cambiar un adaptador — el núcleo no se entera.

### 4. Principios Subyacentes

La Arquitectura Hexagonal no introduce ideas nuevas desde cero: es una forma concreta de aplicar principios ya establecidos en el diseño de software:

- **Inversión de Dependencias (el "D" de SOLID)**: los módulos de alto nivel (el dominio) no dependen de módulos de bajo nivel (infraestructura); ambos dependen de abstracciones (los puertos).
- **Segregación de Interfaces**: los puertos deben ser específicos y pequeños, describiendo exactamente lo que el núcleo necesita, evitando interfaces "genéricas" sobrecargadas.
- **Separación de responsabilidades**: la lógica de negocio y los detalles técnicos se mantienen en capas conceptualmente distintas, aunque no necesariamente en "capas" en el sentido de una arquitectura por capas tradicional.

### 5. Diferencia con Arquitectura en Capas Tradicional

| Aspecto | Capas Tradicionales | Hexagonal |
|---|---|---|
| Dependencia | Negocio depende de datos | Todo depende del núcleo |
| Cambio de tecnología | Puede afectar la lógica de negocio | Solo se reemplaza un adaptador |
| Entrada/salida | No se distingue | Explícitamente separadas |

### 6. Relación con Otros Enfoques

Comparte su premisa central —dependencias apuntando siempre hacia el núcleo— con **Clean Architecture** y **Onion Architecture**, y suele usarse junto con **DDD** para modelar el dominio que el hexágono protege.

### 7. Beneficios y Costos
99
- **Mayor cantidad de artefactos**: se introducen interfaces y clases adicionales (puertos) que no existirían en una implementación directa, lo que puede sentirse como sobreingeniería en sistemas muy pequeños o de vida corta.
- **Curva de aprendizaje**: requiere que el equipo entienda y respete la disciplina de nunca hacer referencia directa a infraestructura desde el núcleo.
- **No resuelve todo por sí sola**: Hexagonal organiza las dependencias, pero no dicta cómo modelar el dominio (para eso se apoya en principios como DDD) ni cómo comunican los módulos entre sí a nivel de todo el sistema (para eso se combina con estilos como microservicios o event-driven).
