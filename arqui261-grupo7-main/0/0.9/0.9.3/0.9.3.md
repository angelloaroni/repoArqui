# 0.9.3. Integrante 3

# Arquitectura Microkernel

## Desarrollo Conceptual

### 1. Definición

La **Arquitectura Microkernel** (también llamada arquitectura de *plugin* o de micro-núcleo) organiza un sistema en dos partes claramente separadas:

1. Un **núcleo mínimo (Core)** estable, responsable de los servicios esenciales y de las reglas de comunicación.
2. Un conjunto de **plugins** (o módulos extendibles) que aportan funcionalidades concretas sin modificar el núcleo.

La idea central es que el Core permanece **pequeño, predecible y reutilizable**, mientras que las capacidades del producto **crecen o se reducen conectando y desconectando plugins** a través de una interfaz común.

Este estilo se inspira en el diseño de sistemas operativos de microkernel (donde el núcleo solo gestiona servicios básicos y el resto vive fuera) y se aplica a software de aplicación: IDEs, navegadores, sistemas de reglas de negocio, plataformas de integración y demos educativas como la implementada para este tema.

El nombre no implica que el “núcleo” sea trivial: implica que **solo contiene lo indispensable** para registrar, descubrir y orquestar extensiones, sin absorber la lógica específica de cada funcionalidad.

---

### 2. Problema que Resuelve

Cuando todas las funcionalidades viven mezcladas en un solo bloque (monolito rígido), aparecen varios problemas:

- **Difícil de evolucionar**: agregar una capacidad nueva obliga a tocar el corazón del sistema y recompilar o redesplegar todo.
- **Alto acoplamiento**: un cambio en una funcionalidad puede romper otras, porque comparten código y dependencias internas.
- **Poca flexibilidad para el producto**: no es sencillo activar/desactivar features por cliente, entorno o experimento.
- **Pruebas costosas**: validar una función menor implica cargar (y arriesgar) el resto del sistema.

La Arquitectura Microkernel responde a esto separando **lo estable** (Core) de **lo variable** (plugins). El Core define el contrato; los plugins implementan capacidades. Así, el sistema puede extenderse sin reescribir el núcleo.

---

### 3. Conceptos Clave

#### 3.1 El Núcleo (Core)

Es la parte mínima y estable del sistema. Típicamente se encarga de:

- Definir la **interfaz** que todo plugin debe cumplir.
- **Registrar** y **listar** plugins disponibles.
- **Invocar** plugins a petición del usuario o de otro componente.
- Ofrecer servicios comunes (configuración básica, ciclo de vida, manejo de errores al ejecutar un plugin).

El Core **no conoce** la lógica interna de cada plugin. Solo trabaja con abstracciones.

En la demo de este tema, el Core está en `microkernel_demo/core/` e incluye:

| Archivo | Rol |
|---------|-----|
| `plugin.py` | Interfaz abstracta `Plugin` (`get_name`, `execute`) |
| `plugin_manager.py` | Registro, listado y ejecución de plugins |
| `main.py` | Arranque, descubrimiento dinámico y menú interactivo |

---

#### 3.2 Plugins (Extensiones)

Un **plugin** es un módulo independiente que implementa una funcionalidad concreta respetando el contrato del Core.

Características típicas:

- Es **autocontenido**: su lógica vive fuera del núcleo.
- Puede **agregarse o quitarse** sin modificar el Core.
- Se identifica con un nombre visible para el usuario.
- Expone una operación de ejecución (en la demo: `execute()`).

En la demo, los plugins viven en `plugins/` (por ejemplo Saludo, Fecha, Calculadora, Número aleatorio, Letras aleatorias). Cada uno hereda de `Plugin` y define su propio comportamiento.

---

#### 3.3 Contrato / Interfaz de Plugin

El contrato es la “regla de juego” entre Core y plugins. En la demo es una clase abstracta:

- `get_name()`: nombre que aparece en el menú.
- `execute()`: acción que realiza el plugin.

Gracias a este contrato, el `PluginManager` puede ejecutar cualquier plugin sin importar si saluda, calcula o genera un número aleatorio.

---

#### 3.4 Plugin Manager (Registro y Orquestación)

El **Plugin Manager** es el componente del Core que:

- Mantiene la lista de plugins registrados.
- Los expone al menú o a otros clientes.
- Delega la ejecución al plugin seleccionado.
- Aísla fallos: si un plugin falla, el Core puede capturar el error sin caerse por completo.

Es el “puente” operativo entre la interfaz abstracta y las implementaciones concretas.

---

#### 3.5 Descubrimiento dinámico

Además del registro manual, muchos sistemas microkernel **descubren** plugins automáticamente (carpeta, manifiesto, classpath, etc.).

En la demo, `main.py` escanea `plugins/*_plugin.py`, carga las clases que heredan de `Plugin` y las registra. Por eso **agregar un plugin nuevo no requiere editar el Core**: basta crear el archivo y reiniciar.

---

### 4. Principios Subyacentes

La Arquitectura Microkernel aplica principios clásicos de diseño de software:

- **Inversión de Dependencias (SOLID)**: el Core define la abstracción (`Plugin`); los plugins dependen de ella, no al revés.
- **Abierto/Cerrado**: el sistema está abierto a extensión (nuevos plugins) y cerrado a modificación del núcleo.
- **Separación de responsabilidades**: el Core orquesta; cada plugin resuelve una capacidad puntual.
- **Bajo acoplamiento / alta cohesión**: los plugins no se conocen entre sí; solo comparten el contrato del Core.
- **Sustitución**: cualquier implementación válida del contrato puede reemplazar a otra sin cambiar el núcleo.

---

### 5. Diferencia con Otros Estilos

| Aspecto | Monolito rígido | Microservicios | Microkernel |
|---------|-----------------|----------------|-------------|
| Unidad de extensión | Cambiar el mismo código base | Nuevo servicio desplegable | Nuevo plugin |
| Núcleo | No hay separación clara | Cada servicio es autónomo | Core mínimo compartido |
| Despliegue típico | Una sola unidad | Varios procesos/red | Suele ser un proceso con módulos cargables |
| Acoplamiento | Alto | Bajo entre servicios (vía red) | Bajo entre plugins (vía contrato) |
| Ideal cuando… | El dominio es estable y pequeño | Escala y equipos independientes | Se necesitan features enchufables |

Microkernel **no compite** necesariamente con microservicios: a veces un microservicio interno se diseña con plugins, o un producto de escritorio usa microkernel sin ser distribuido.

---

### 6. Relación con DriveShare y con la Demo

DriveShare, como producto, se organiza por módulos (Usuarios, Catálogo, Reservas, Pagos, etc.). La idea microkernel es especialmente útil cuando se desea:

- Activar o desactivar capacidades (por ejemplo, notificaciones, reglas de precio, integraciones).
- Extender el sistema sin reescribir el núcleo de orquestación.
- Mantener un contrato estable entre el “cerebro” del sistema y sus extensiones.

La **demo educativa** (`microkernel_demo`) no pretende reemplazar la arquitectura completa de DriveShare; sirve para demostrar, de forma tangible, el principio:

> El Core permanece igual; las funcionalidades crecen como plugins.

Flujo de la demo:

1. El Core descubre e instancia los plugins.
2. El `PluginManager` los registra.
3. El menú lista `get_name()` de cada uno.
4. Al elegir una opción, el Core llama `execute()` sin conocer la implementación interna.

---

### 7. Beneficios y Costos

#### Beneficios

- Extensibilidad sin modificar el núcleo.
- Mejor aislamiento de fallos por funcionalidad.
- Facilita personalización (activar/desactivar plugins).
- Favorece el trabajo en paralelo: distintos desarrolladores pueden crear plugins distintos.
- Claridad pedagógica y de mantenimiento: se ve qué es estable y qué es variable.

#### Costos

- Hay que diseñar bien el contrato del plugin; un contrato mal pensado limita o acopla todo.
- Más artefactos (interfaz, manager, carga dinámica) que en un script monolítico.
- Complejidad de versionado y compatibilidad entre Core y plugins.
- El descubrimiento dinámico exige disciplina (nombres, carpetas, manejo de errores al cargar).
- No es la mejor opción para sistemas muy pequeños donde una sola funcionalidad basta.
