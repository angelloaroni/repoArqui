# 5.4. Módulo 4 / Integrante 4

## Módulo de pago

## Tácticas de disponibilidad

### Escenario

| Atributo de Calidad | Estímulo | Fuente del Estímulo | Artefacto | Entorno | Respuesta | Medida de Respuesta |
| --- | --- | --- | --- | --- | --- | --- |
| Disponibilidad | El gateway de pago externo no responde | Proveedor de pagos | Módulo de Pagos | Operación normal | El sistema muestra un mensaje de error al usuario e indica que puede reintentar más tarde | El usuario recibe la notificación en menos de 5 segundos y no se genera ningún cobro |

### Táctica Elegida
Para alcanzar la medida de respuesta deseada en este caso, se elige la táctica de disponibilidad de Circuit Breaker. A continuación se documenta los detalles de la decisión tomada.

### Documentación de la Decisión (ADR)

**Título:**  
- Elección entre Circuit Breaker vs Retry con Backoff Exponencial para el Módulo de Pagos.

**Contexto:**  
- El sistema depende de un proveedor de pagos externo para procesar los cobros a los arrendatarios. La indisponibilidad del proveedor podría acumular solicitudes en espera, saturar recursos internos y generar tiempos de espera prolongados o lo más crítico cobros duplicados. El riesgo es especialmente crítico en periodos de alta demanda (feriados, fines de semana largos) donde el impacto es directamente en la confianza del usuario.

**Alternativas:**  

1. **Circuit Breaker**
    - Detecta cuando el gateway de pagos comienza a fallar repetidamente. Tras superar un límite o umbral configurable de errores consecutivos, "abre el circuito" (Open) y rechaza nuevas solicitudes de forma inmediata sin intentar contactar al proveedor caído.
    - Incluye un estado semi-abierto (Half-Open) que permite probar periódicamente si el gateway se recuperó, cerrando el circuito automáticamente cuando responde con éxito.
    - Protege los recursos internos del módulo de pagos y permite mostrar respuestas rápidas al usuario, incluso cuando el servicio externo está caído.
    - Su implementación requiere definir límites de errores y tiempos de espera, pero existen librerías que facilitan este proceso, como resilience en Node.js.

2. **Lista de espera con reintentos automáticos**
    - Ante un fallo, el sistema reintenta la solicitud al gateway tras intervalos de espera crecientes.
    - Útil para fallos transitorios muy breves, pero en caídas prolongadas del gateway puede mantener al usuario esperando varios segundos antes de recibir un error.
    - No protege contra saturación de recursos: múltiples usuarios concurrentes reintentando simultáneamente pueden sobrecargar tanto el gateway como el propio módulo de pagos.
    - Puede combinarse con Circuit Breaker como mecanismo complementario dentro del estado semi-abierto.

**Criterios de Elección:**  
- Velocidad de respuesta al usuario ante fallo del gateway.
- Protección de recursos internos ante alta concurrencia.
- Prevención de cobros duplicados o transacciones inconsistentes.
- Capacidad de recuperación automática cuando el proveedor vuelve a estar disponible.
- Complejidad de implementación aceptable para el contexto del proyecto.

**Decisión:** 
- Se elige el **Circuit Breaker**.

**Sustento:** 
- Debido a que el módulo de pagos procesa transacciones críticas, un fallo podría generar cobros duplicados o pérdidas de pago que afecten la confianza de los usuarios. Por ello, se elige la táctica Circuit Breaker, ya que permite responder rápidamente cuando el gateway falla, evitando la sobrecarga del sistema y manteniendo la estabilidad del servicio. Además, puede restablecer automáticamente las operaciones cuando el proveedor vuelve a estar disponible.


## Tácticas de seguridad

### Escenario
| Atributo de Calidad | Estímulo | Fuente del Estímulo | Artefacto | Entorno | Respuesta | Medida de Respuesta |
| --- | --- | --- | --- | --- | --- | --- |
| Seguridad | Alguien intenta pagar con una tarjeta robada | Usuario malintencionado | Módulo de Pagos – validación | Cualquier momento del día | El sistema detecta que la tarjeta es sospechosa, bloquea el pago y avisa al administrador | El 100 % de pagos fraudulentos son bloqueados antes de procesarse |

### Táctica Elegida
Para alcanzar la medida de respuesta deseada, se elige la táctica de seguridad de Detectar Intrusos (Intrusion Detection). A continuación se documenta los detalles de la decisión tomada.

### Documentación de la Decisión (ADR)
**Título**  
- Elección entre Detección de Intrusos (reglas + scoring) vs Delegación total al gateway externo.

**Contexto:**
- El sistema procesa pagos entre arrendatarios y propietarios de vehículos, por lo que existe el riesgo de que algunas personas intenten usar tarjetas robadas o datos falsos para hacer reservas sin pagar realmente. Esto podría generar pérdidas económicas y afectar la confianza en la plataforma. Si toda la detección de fraude depende únicamente del gateway de pagos externo, el sistema no tendría control ni visibilidad sobre comportamientos sospechosos antes de enviar la transacción. Por ello, la plataforma necesita contar con sus propias validaciones de seguridad en tiempo real para detectar posibles fraudes de manera más rápida y preventiva.

**Alternativas:** 

1. **Detección de Intrusos con reglas y scoring interno**
    - El módulo de pagos analiza cada transacción contra un conjunto de reglas configurable antes de enviarla al gateway, revisando señales sospechosas como varios intentos fallidos, datos inconsistentes, montos atípicos o velocidad de transacciones.
    - Si la transacción supera un umbral de riesgo, se bloquea de forma inmediata y se genera una alerta al administrador.
    - Proporciona visibilidad interna sobre patrones de fraude y permite ajustar las reglas sin depender del proveedor externo.
    - Requiere diseño e implementación de las reglas de detección, pero no depende de servicios adicionales de terceros.

2. **Delegación total al gateway externo**
    - Se confía en que el proveedor de pagos detecte y bloquee transacciones fraudulentas por su cuenta, sin validación previa en el módulo de pagos.
    - Reduce el esfuerzo de implementación, pero deja a la plataforma sin control ni visibilidad sobre el fraude.
    - Si el proveedor falla en detectar una transacción fraudulenta, el sistema no tiene ninguna barrera adicional de protección.
    - No permite generar alertas internas ni auditar los intentos de fraude dentro de la propia plataforma.

**Criterios de Elección:**  
- Capacidad de bloqueo antes de que la transacción llegue al gateway.
- Visibilidad y trazabilidad interna de intentos fraudulentos.
- Independencia respecto al proveedor externo de pagos.
- Tiempo de respuesta para generar la alerta al administrador.
- Complejidad de implementación aceptable para el contexto del proyecto.

**Decisión:** 
- Se elige la **Detección de Intrusos**.

**Sustento:**
- Dado que el módulo de pagos es el componente más sensible del sistema, depender únicamente del gateway externo para detectar fraudes representa un riesgo importante para la plataforma. Por eso, se implementan reglas de validación internas que permiten identificar y bloquear transacciones sospechosas antes de enviarlas al proveedor de pagos. Esto ayuda a reducir posibles pérdidas económicas, proteger la confianza de los usuarios y mantener un mejor control sobre actividades fraudulentas. Además, el sistema puede registrar y monitorear los intentos de fraude en tiempo real, facilitando la supervisión y el cumplimiento de requisitos de seguridad.

### Escenario

| Mantenibilidad | Incorporación de un nuevo método de pago | Equipo de desarrollo | Módulo de Métodos de Pago | Sprint de desarrollo iterativo | El sistema permite agregar el nuevo método sin modificar el flujo de pago existente | El cambio se implementa en un máximo de 5 días sin afectar los métodos ya disponibles |

### Táctica Elegida
Para alcanzar la medida de respuesta deseada, se elige la táctica de rendimiento de Gestión de la Demanda mediante Cola de Solicitudes (Queue-Based Load Leveling). A continuación se documenta los detalles de la decisión tomada.

### Documentación de la Decisión (ADR)
**Título**: 
- Elección entre Cola de Solicitudes (Queue-Based Load Leveling) vs Escalado Horizontal.

**Contexto:** 
- El sistemas puede experimentar picos de demandas en los días de feriados largos o temporada alta, donde varios usuarios quieren confirmar sus reservas de vehículos de manera simultánea. Si el sistema no maneja correctamente este aumento de solicitudes, el módulo de pagos podría saturarse, generar errores o incluso realizar cobros duplicados por reintentos no controlados. Por ello, la plataforma necesita una solución que organice y controle las transacciones durante estos picos de actividad, asegurando que cada pago se procese una sola vez y manteniendo una respuesta rápida para los usuarios.

**Alternativas:**

1. **Cola de Solicitudes (Queue-Based Load Leveling)**
- Las solicitudes de pago entrantes se depositan en una cola persistente. Un conjunto de workers consume la cola a un ritmo controlado y se comunica con el gateway de pagos de forma ordenada.
- Desacopla la recepción de solicitudes de su procesamiento, protegiendo tanto el módulo interno como el gateway externo de picos de carga.
- Garantiza que cada solicitud se procese exactamente una vez mediante mecanismos de idempotencia, eliminando el riesgo de cobros duplicados.
- Permite escalar los workers de forma independiente si la demanda crece de manera sostenida.
- Introduce una pequeña latencia adicional respecto al procesamiento directo, pero dentro del umbral de ≤ 10 s definido en el escenario.

2. **Escalado Horizontal del servicio de pagos**
- Se utilizan múltiples instancias del servicio de pagos para atender solicitudes al mismo tiempo, distribuyendo la carga mediante un balanceador.
- Reduce los tiempos de respuesta cuando hay muchos usuarios realizando pagos simultáneamente.
- No existe un buen control de las transacciones; pueden ocurrir cobros duplicados debido a reintentos o solicitudes procesadas al mismo tiempo.
- Requiere mayor costo operativo y coordinación entre las instancias para mantener el estado correcto de cada transacción.


**Criterios de Elección:**
- Protección del gateway ante picos de demanda.
- Garantía de que cada pago se procese una sola vez, evitando cobros duplicados.
- Tiempo de respuesta adecuado para los usuarios incluso cuando hay muchas transacciones al mismo tiempo.
- Tasa de error bajo carga concurrente.
- Complejidad y costo de implementación aceptables para el contexto del proyecto.

**Desicion:** 
- Se elige la **Cola de Solicitudes (Queue-Based Load Leveling).***.

**Sustento:**
- Durante periodos de alta demanda, el mayor riesgo  no es solo la latencia, sino que un pago pueda procesarse más de una vez. Un cobro duplicado puede afectar tanto a los usuarios como a la reputación. Por ello, se utiliza una cola de solicitudes que organiza los pagos y los procesa de forma controlada, evitando sobrecargas y reduciendo el riesgo de errores. Además, mediante mecanismos de idempotencia, se garantiza que cada transacción se procese una sola vez. Aunque el escalado horizontal puede ayudar a futuro, no ofrece las mismas garantías de integridad que esta solución.

### Táctica Elegida
Para alcanzar la medida de respuesta deseada, se elige la táctica de mantenibilidad de Uso de Intermediario mediante el patrón Adaptador (Adapter/Strategy). A continuación se documenta los detalles de la decisión tomada.


### Documentación de la Decisión (ADR)
**Título**: 
- Elección entre patrón Adaptador con interfaz común vs implementación directa por método de pago para la incorporación de nuevos métodos en el Módulo de Pagos.

**Contexto:** 
- DriveShare integra sus pagos a través de un proveedor de pagos, que soporta múltiples métodos como tarjetas de crédito/débito, Yape, Plin y potencialmente otros que puedan implementarse en un futuro según la evolución del negocio. Sin una abstracción adecuada, cada nuevo método de pago requeriría modificar el flujo central de cobro, aumentando el riesgo de introducir errores en funcionalidad ya validada. El equipo necesita una estructura que permita extender los métodos disponibles de forma aislada, sin regresiones en los métodos existentes y dentro de los tiempos de un sprint normal.

**Alternativas:**

1. **Patrón Adaptador con interfaz común (Use an Intermediary)**
- Se define una interfaz común para manejar las operaciones principales de pago.
- Cada método de pago se implementa como un adaptador independiente que encapsula su lógica específica.
- El flujo principal de pagos trabaja únicamente con la interfaz común, sin depender de implementaciones concretas.
- Permite agregar nuevos métodos de pago sin modificar el flujo central.
- Facilita las pruebas, el mantenimiento y la escalabilidad del módulo.

2. **Implementación directa por método de pago**
- El flujo central de cobro contiene lógica condicional para manejar cada método de pago directamente.
- Su implementación inicial es más simple.
- Cada nuevo método requiere modificar el flujo principal.
- Aumenta el riesgo de errores y dificulta el mantenimiento a medida que crecen las integraciones.
- Las pruebas y actualizaciones se vuelven más complejas con el tiempo.


**Criterios de Elección:**
- Facilidad para incorporar nuevos métodos de pago.
- Bajo impacto sobre funcionalidades existentes.
- Facilidad de mantenimiento y pruebas.
- Reducción del riesgo de regresiones.
- Tiempo de implementación acorde al límite.

**Decisión:**
- Se elige el **patrón Adaptador con interfaz común**.

**Sustento:**
- Debido a que el sistema está diseñado para soportar diferentes métodos de pago y poder agregar nuevos en el futuro según las necesidades del negocio. Si toda la lógica de pagos estuviera mezclada en un solo módulo, el sistema sería más difícil de mantener y modificar con el tiempo. Por ello, se utiliza el patrón Adaptador, que permite que cada método de pago funcione como un componente independiente. De esta manera, se pueden agregar, reemplazar o actualizar métodos de pago sin afectar el funcionamiento principal del sistema. Esto facilita el mantenimiento del módulo y permite incorporar nuevos métodos de pago en poco tiempo y con menor riesgo de errores.
