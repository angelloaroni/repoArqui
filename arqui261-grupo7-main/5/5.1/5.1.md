# TACT-01: Disponibilidad
## Escenario

|--------------|-------------------|-----------|---------------------|-----------|----------|------------|--------------------|
| ESC-R02 | Disponibilidad | Fallo de servicios asociados a autenticación y recuperación de cuentas | Servicio externo de correo o red | Servicio de Autenticación y Recuperación de Contraseña-Modulo de Usuario| Operación normal | El sistema reintenta operaciones y mantiene la continuidad del acceso | Recuperación ≤ 60 s; disponibilidad ≥ 99.9% |

## Táctica Elegida

En este caso, para poder alcanzar los niveles de respuesta definidos en el escenario (recuperación menor o igual a 60 segundos y disponibilidad mínima de 99.9%), se ha elegido la táctica de disponibilidad **Reintentos (Retry)**. A continuación se documentan los detalles de la decisión.

# Documentación de la Decisión (ADR)
## Titulo:
- Elección entre Reintentos (Retry) vs Redundancia Activa 

## Contexto

- La plataforma DriveShare permite a propietarios y arrendatarios acceder a sus cuentas mediante autenticación con credenciales propias y, opcionalmente, mediante servicios externos de autenticación. Asimismo, ofrece mecanismos de recuperación de contraseña basados en correo electrónico. Durante la operación normal pueden producirse fallos temporales en servicios externos de correo o problemas de conectividad de red que afecten estos procesos. La indisponibilidad de dichos servicios podría retrasar la recuperación de acceso de los usuarios y afectar la continuidad de ciertas funcionalidades del módulo de Usuarios. La solución se despliega sobre infraestructura en la nube, lo que facilita la implementación de tácticas de disponibilidad orientadas a la recuperación automática de operaciones y al mantenimiento de los niveles de servicio establecidos.

## Alternativas

### 1. Reintentos (Retry)

La aplicación detecta errores temporales de comunicación y vuelve a intentar automáticamente la operación después de un intervalo configurado.

- Asume que la falla es temporal y que el servicio puede recuperarse después de algunos segundos.
- Permite volver a ejecutar operaciones fallidas sin intervención del usuario.
- Tiene un bajo costo de implementación e infraestructura.
- Requiere definir límites de reintentos para evitar sobrecarga o ciclos infinitos.
- Resulta especialmente útil cuando la falla proviene de servicios externos como proveedores de correo electrónico o problemas momentáneos de conectividad.

### 2. Redundancia Activa

Se mantienen varios servidores activos, todos recibiendo solicitudes. Si uno falla, las solicitudes son automáticamente redirigidas a otro servidor activo sin interrupción.

- Proporciona tiempos de conmutación imperceptibles para el usuario final, permitiendo mantener una solución en alta disponibilidad.
- Garantiza la continuidad del servicio incluso ante fallas de infraestructura.
- Requiere una mayor inversión en infraestructura y monitoreo constante.
- Incrementa la complejidad operativa del sistema.
- Resulta más adecuada para fallas de componentes internos críticos que para problemas temporales de servicios externos.

## Criterios de Elección

- Capacidad para recuperarse de fallas temporales en servicios externos.
- Impacto sobre la experiencia del usuario 
- Costo de implementación y operación.
- Facilidad de integración con la arquitectura existente.
- Cumplimiento de los tiempos de recuperación establecidos.

## Decisión

Se elige la táctica de disponibilidad **Reintentos (Retry)**.

## Sustento

Debido a que el módulo de Usuarios depende de servicios externos, es necesario contar con un mecanismo que permita enfrentar fallas temporales sin afectar significativamente la continuidad del servicio. La táctica de **Reintentos (Retry)** permite que, ante una operación fallida, el sistema realice nuevos intentos de forma automática dentro de límites previamente definidos, aumentando la probabilidad de completar exitosamente la operación sin intervención del usuario.


# Demo Reintentos (Retry)

## Descripción General

Este proyecto establece una demostración de la táctica de disponibilidad **Reintentos (Retry)**. La solución está compuesta por un servicio de autenticación desarrollado en Node.js y un servicio de correo simulado. Cuando un usuario solicita la recuperación de contraseña, el servicio de autenticación intenta enviar un correo electrónico utilizando el servicio externo.

Para demostrar la táctica, el servicio de correo simula una falla temporal durante la primera solicitud recibida. El módulo de autenticación detecta el error y ejecuta automáticamente un nuevo intento después de un tiempo configurado. Si el servicio vuelve a estar disponible, la operación se completa exitosamente sin intervención del usuario.

La demostración permite observar cómo la táctica de Reintentos contribuye a mantener la disponibilidad del sistema ante fallas temporales de servicios externos.

## Servicios

### auth-service

Aplicación desarrollada en Node.js encargada de procesar solicitudes de recuperación de contraseña e implementar la lógica de reintentos.

### fake-mail-service

Servicio simulado de correo electrónico utilizado para representar un proveedor externo. La primera solicitud falla intencionalmente y las siguientes son procesadas correctamente.

### Requisitos Previos

- Docker
- Docker Compose

## Ejecutar la Demo

### 1. Clonar el repositorio

```bash
git clone https://github.com/ulima-arqsoft/arqui261-grupo7.git
```

### 2. Navegar hasta la carpeta de la demostración

```bash
cd arqui261-grupo7/5/5.1/demo-disponibilidad
```

### 3. Levantar todos los servicios con Docker Compose

```bash
docker compose up --build
```

Con este comando se construirán las imágenes Docker y se iniciarán los servicios necesarios para la demostración. El servicio de autenticación estará disponible en el puerto **3000** y el servicio de correo simulado en el puerto **3001**.

### 4. Reiniciar el escenario de prueba

Para reiniciar el contador del servicio de correo y volver a simular la falla temporal inicial, ejecutar:

```bash
curl -X POST http://localhost:3001/reset
```

Respuesta esperada:

```json
{
  "success": true,
  "message": "Counter reset"
}
```

### 5. Ejecutar la demostración

Realizar una solicitud de recuperación de contraseña:

```bash
curl -X POST http://localhost:3000/recover-password
```

Respuesta esperada:

```json
{
  "success": true,
  "attempts": 2,
  "recoveryTimeMs": 5023,
  "response": {
    "success": true,
    "message": "Mail sent"
  }
}
```

Observe que el valor de `attempts` es igual a **2**, indicando que la operación requirió un reintento antes de completarse exitosamente.

### 6. Verificar la ejecución de la táctica

Consultar los registros del servicio de autenticación:

```bash
docker compose logs auth-service
```

Resultado esperado:

```text
Attempt 1
Attempt 1 failed
Retrying in 5 seconds...

Attempt 2
Mail sent successfully
Recovery time: 5023 ms
```

### 7. Verificar el comportamiento del servicio externo

Consultar los registros del servicio de correo:

```bash
docker compose logs fake-mail-service
```

Resultado esperado:

```text
Mail request #1
Simulating temporary failure

Mail request #2
Mail sent successfully
```

Observe que el primer intento falla deliberadamente y el sistema ejecuta automáticamente un segundo intento, logrando completar la operación en aproximadamente 5 segundos. Esto demuestra la aplicación de la táctica de disponibilidad **Reintentos (Retry)** para recuperarse de fallas temporales en servicios externos.


## Beneficios

- La aplicación recupera automáticamente una operación que inicialmente falla debido a la indisponibilidad temporal del servicio de correo.
- No es necesario que el usuario vuelva a ejecutar la solicitud de recuperación de contraseña.
- La operación se completa exitosamente mediante un segundo intento realizado por el sistema.
- Los registros permiten verificar claramente la detección de la falla y la ejecución del reintento automático.
- La recuperación se realiza en aproximadamente 5 segundos, manteniéndose dentro del tiempo objetivo definido para el escenario.
- La demostración evidencia cómo una falla temporal de un servicio externo puede resolverse sin interrumpir la continuidad del proceso.

# Táctica Elegida

En este caso, para poder alcanzar los niveles de respuesta definidos en el escenario (realizar modificaciones con impacto mínimo sobre otros componentes y sin interrumpir el servicio), se ha elegido la táctica de mantenibilidad **Parametrización**. Esta táctica permite desacoplar configuraciones y elementos sujetos a cambios frecuentes de la lógica principal del sistema, facilitando su evolución futura y reduciendo el esfuerzo asociado a tareas de mantenimiento.

# Documentación de la Decisión (ADR)

## Elección entre Disminuir Acoplamiento (Encapsulamiento) vs Parametrización

## Contexto

DriveShare se encuentra en constante evolución debido a la incorporación de nuevas funcionalidades, integraciones externas y mejoras relacionadas con la seguridad y autenticación de usuarios. Estos cambios pueden requerir modificaciones frecuentes sobre configuraciones, credenciales, claves criptográficas y otros elementos que forman parte de la plataforma.

Si estos elementos se encuentran estrechamente ligados a la lógica de negocio, cualquier modificación podría generar impactos sobre múltiples componentes, aumentando el esfuerzo de mantenimiento y el riesgo de introducir errores. Por ello, se requiere una solución que permita realizar cambios de manera controlada, reduciendo el impacto sobre el resto de la arquitectura y facilitando la evolución continua del sistema.

## Alternativas

### 1. Disminuir Acoplamiento (Encapsulamiento)

Consiste en proveer una interfaz específica para un módulo, definiendo claramente sus responsabilidades y ocultando los detalles internos de implementación.

- Reduce la probabilidad de que un cambio afecte otros módulos del sistema.
- Permite modificar implementaciones internas manteniendo estable la interfaz pública.
- Facilita la evolución independiente de los componentes.
- Disminuye el impacto de futuros cambios sobre la arquitectura.
- Requiere definir correctamente los límites y responsabilidades de cada módulo.

### 2. Parametrización

Consiste en externalizar configuraciones y parámetros para evitar modificaciones directas en el código fuente cuando se requieren cambios en el comportamiento del sistema.

- Incrementa la flexibilidad de la solución.
- Reduce el esfuerzo necesario para realizar modificaciones futuras.
- Permite adaptar configuraciones sin alterar la lógica de negocio.
- Facilita la incorporación de nuevos requerimientos o integraciones.
- Disminuye el costo de mantenimiento a largo plazo.

## Criterios de Elección

Reducir el impacto de cambios futuros, evitar modificaciones repetidas sobre la lógica de negocio y facilitar la actualización de configuraciones sin afectar otros componentes del sistema.

## Decisión y Sustento

El módulo gestionará las configuraciones sujetas a cambios frecuentes mediante parámetros almacenados externamente en HashiCorp Vault, evitando que estos valores se encuentren definidos directamente en el código fuente. Elementos como versiones de claves, configuraciones de autenticación o futuras credenciales podrán administrarse desde un punto centralizado sin requerir modificaciones en los componentes consumidores.

De esta manera, actualizar una configuración requerirá únicamente modificar el valor correspondiente en Vault, permitiendo que la aplicación continúe operando sin afectar la lógica principal ni otros módulos de la plataforma. Esto reduce el esfuerzo de mantenimiento, facilita la evolución futura del sistema y permite implementar cambios de forma controlada.



# Demo - Parametrización de Configuración de Autenticación mediante HashiCorp Vault

## Descripción General

Este proyecto establece una demostración de la táctica de mantenibilidad **Parametrización**, mediante la cual se pueden modificar configuraciones del sistema sin necesidad de alterar el código fuente. En este caso, la configuración asociada a la versión activa de una clave utilizada por el módulo de autenticación se encuentra almacenada externamente en HashiCorp Vault.

La aplicación consulta dinámicamente dicha configuración desde Vault y muestra la versión actualmente activa. Cuando el valor es modificado desde la interfaz web de Vault, la aplicación refleja automáticamente el nuevo valor sin necesidad de recompilar el sistema, modificar la lógica de negocio o afectar otros componentes de la solución.

La demostración permite evidenciar cómo la parametrización facilita la evolución del sistema, reduce el impacto de futuros cambios y disminuye el esfuerzo asociado a tareas de mantenimiento.

## Táctica Elegida

En este caso, para cumplir los niveles de protección establecidos en el escenario, se elige la táctica de seguridad **Encriptar los Datos**. A continuación, se documentan los detalles de la decisión.

## Documentación de la Decisión (ADR)

### Título

- Elección entre Encriptar los Datos y Detectar Intrusos para la protección de credenciales en el Módulo de Usuarios.

### Contexto

- La plataforma permite que propietarios y arrendatarios gestionen sus cuentas y accedan a las funcionalidades del sistema mediante procesos de autenticación. Debido a que el módulo de Usuarios almacena y procesa credenciales e información sensible, un acceso no autorizado podría comprometer cuentas de usuario y afectar la confianza en la plataforma. La operación se realiza a través de servicios web accesibles desde Internet, lo que hace necesario implementar tácticas de seguridad orientadas a proteger la confidencialidad de los datos y reducir el impacto de posibles ataques.

### Alternativas

#### 1. Encriptar los Datos

- Protege las credenciales almacenadas y transmitidas mediante mecanismos de cifrado.
- Reduce el impacto en caso de interceptación o acceso no autorizado a la información.
- Mantiene la confidencialidad de los datos sensibles incluso si ocurre una filtración parcial.

#### 2. Detectar Intrusos

- Analiza patrones de tráfico y solicitudes para identificar comportamientos maliciosos.
- Detecta intentos de acceso sospechosos o actividades potencialmente peligrosas.
- Requiere mecanismos adicionales para prevenir o mitigar los ataques detectados.

### Criterios de Elección

- Protección de credenciales frente a accesos no autorizados.
- Preservación de la confidencialidad de la información sensible.
- Reducción del impacto ante una posible filtración de datos.

### Decisión

- Se elige la táctica **Encriptar los Datos**.

### Sustento

Debido a que el módulo de Usuarios gestiona credenciales e información sensible de propietarios y arrendatarios, es necesario implementar mecanismos que protejan estos datos frente a intentos de acceso no autorizado. La táctica de **Encriptar los Datos** garantiza que las credenciales permanezcan protegidas incluso si son interceptadas durante su transmisión o si ocurre una exposición de la información almacenada.

## Documentación de la Decisión (ADR)

### Título

* Elección entre Limitar la Respuesta de Eventos vs Introducir Concurrencia para el Módulo de Login.

### Contexto

La plataforma permite que propietarios y arrendatarios accedan a sus cuentas mediante procesos de autenticación. Durante horarios de alta actividad pueden producirse múltiples solicitudes de inicio de sesión de manera simultánea, incrementando la demanda sobre el módulo de Login. Por ello, es necesario implementar tácticas de rendimiento que permitan mantener tiempos de respuesta aceptables durante periodos de alta concurrencia.

### Alternativas

#### 1. Limitar la Respuesta de Eventos

* Controla la cantidad de solicitudes procesadas en un determinado intervalo de tiempo.
* Reduce el riesgo de saturación de recursos durante periodos de alta demanda.
* Contribuye a mantener tiempos de respuesta estables.

#### 2. Introducir Concurrencia

* Permite procesar múltiples solicitudes de manera paralela.
* Reduce tiempos de bloqueo entre solicitudes.
* Requiere una gestión más compleja de recursos y procesos concurrentes.

### Criterios de Elección

* Capacidad para mantener tiempos de respuesta 
* Soporte para una alta cantidad de usuarios concurrentes.
* Prevención de la saturación de recursos 

### Decisión

* Se elige la táctica **Limitar la Respuesta de Eventos**.

### Sustento

Debido a que el módulo de Login puede recibir un elevado número de solicitudes de autenticación durante horas pico, es necesario implementar mecanismos que eviten la saturación de los recursos del sistema. La táctica de **Limitar la Respuesta de Eventos** permite controlar el flujo de solicitudes procesadas, contribuyendo a mantener tiempos de respuesta aceptables incluso bajo condiciones de alta concurrencia.

## Documentación de la Decisión (ADR)

### Título

* Elección entre Escalabilidad Horizontal (Scale Out) y Escalabilidad Vertical (Scale Up) para el Módulo de Usuarios.

### Contexto

La plataforma permite que propietarios y arrendatarios accedan a sus cuentas mediante procesos de autenticación. Conforme aumenta la cantidad de usuarios registrados y solicitudes de inicio de sesión, el módulo de Usuarios debe mantener tiempos de respuesta estables sin afectar la experiencia de acceso. Por ello, es necesario implementar mecanismos que permitan ampliar la capacidad del sistema de forma eficiente ante el crecimiento de la demanda.

### Alternativas

#### 1. Escalabilidad Horizontal (Scale Out)

* Agrega nuevas instancias del servicio de autenticación para distribuir la carga de trabajo.
* Permite incrementar la capacidad del sistema conforme aumenta la demanda.
* Facilita el crecimiento gradual de la plataforma sin depender de un único servidor.

#### 2. Escalabilidad Vertical (Scale Up)

* Incrementa los recursos de una instancia existente, como memoria o capacidad de procesamiento.
* Requiere menos cambios en la arquitectura inicial.
* Presenta límites físicos y económicos conforme la demanda continúa creciendo.

### Criterios de Elección

* Capacidad para soportar el crecimiento de usuarios.
* Mantenimiento de tiempos de respuesta estables.
* Facilidad para ampliar recursos conforme aumenta la demanda.

### Decisión

* Se elige la táctica **Escalabilidad Horizontal (Scale Out)**.

### Sustento

Debido a que el módulo de Usuarios debe soportar un crecimiento continuo en la cantidad de usuarios y solicitudes de autenticación, es necesario implementar mecanismos que permitan ampliar la capacidad de procesamiento sin afectar el rendimiento del sistema. La táctica de **Escalabilidad Horizontal (Scale Out)** permite distribuir la carga de autenticación entre múltiples instancias, manteniendo tiempos de respuesta estables conforme aumenta la demanda.
