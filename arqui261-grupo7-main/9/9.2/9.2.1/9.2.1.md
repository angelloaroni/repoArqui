# 9.2.1. Objetivo de la iteración

### Propósito

La primera iteración del proceso **Attribute-Driven Design (ADD)** tiene como objetivo definir la estructura general de **DriveShare**, estableciendo los principales elementos arquitectónicos del sistema, las relaciones entre ellos y la distribución inicial de responsabilidades.

Durante esta iteración no se profundiza en el diseño interno de cada módulo funcional, sino que se establece una arquitectura base que servirá como fundamento para las siguientes iteraciones, en las cuales se refinarán la funcionalidad principal del sistema y los atributos de calidad priorizados.

La arquitectura propuesta debe permitir que los módulos de **Usuarios, Catálogo de Vehículos, Reservas, Pagos y Reseñas** puedan desarrollarse de forma independiente, manteniendo una comunicación consistente mediante interfaces bien definidas y una organización común para toda la plataforma.

---

## Drivers que guían la iteración

A partir de la revisión de entradas (Sección 9.1), se identifican los siguientes drivers arquitectónicos que condicionan la estructura general de DriveShare.

| Tipo de Driver | Driver | Influencia sobre esta iteración |
|----------------|--------|---------------------------------|
| Restricción | Aplicación Web basada en arquitectura Cliente-Servidor | La solución debe organizarse mediante una separación clara entre el cliente (Frontend) y el servidor (Backend). |
| Restricción | Comunicación mediante API REST | Todos los módulos deberán comunicarse utilizando interfaces REST bien definidas, favoreciendo el desacoplamiento entre componentes. |
| Restricción | Desarrollo modular por integrantes | Cada módulo deberá desarrollarse de forma independiente sin afectar el funcionamiento del resto del sistema. |
| Restricción | Base de datos centralizada | La información del sistema deberá mantenerse en un repositorio compartido que garantice consistencia e integridad de los datos. |
| Restricción | Componentes especializados | La arquitectura deberá integrar componentes como Storage Component, Cache Component, Database y Search Database para soportar funcionalidades específicas del sistema. |
| Preocupación arquitectónica | Organización modular | La solución deberá dividirse en módulos funcionales con responsabilidades claramente definidas. |
| Preocupación arquitectónica | Separación por capas | Debe existir una separación entre presentación, lógica de negocio y persistencia para facilitar el mantenimiento del sistema. |
| Atributo de Calidad | Mantenibilidad | La estructura general deberá permitir incorporar nuevas funcionalidades sin modificar significativamente la arquitectura existente. |
| Atributo de Calidad | Seguridad | La arquitectura deberá contemplar un punto centralizado para la autenticación, autorización y control de acceso a los diferentes módulos. |
| Atributo de Calidad | Escalabilidad | La distribución de responsabilidades deberá facilitar el crecimiento progresivo de usuarios, vehículos y reservas sin afectar el funcionamiento del sistema. |

---

## Criterio de éxito

La primera iteración se considerará satisfactoria cuando se encuentren definidos:

1. La estructura general de DriveShare y los principales contenedores arquitectónicos del sistema.
2. Las relaciones entre el Frontend, Backend, Base de Datos y componentes especializados.
3. Los patrones arquitectónicos comunes que servirán como base para todos los módulos.
4. La asignación inicial de responsabilidades para los cinco módulos funcionales (**Usuarios, Catálogo de Vehículos, Reservas, Pagos y Reseñas**).
5. La organización por capas y la comunicación entre componentes mediante servicios REST.

Con estos elementos definidos, cada integrante del equipo podrá continuar el diseño detallado de su módulo sobre una arquitectura consistente, modular y alineada con los atributos de calidad identificados durante la revisión de entradas.
