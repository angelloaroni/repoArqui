# 9.1. Revisión de Entradas


### Objetivo

La revisión de entradas tiene como finalidad validar que la información necesaria para iniciar el proceso de diseño arquitectónico de **DriveShare** se encuentre claramente identificada y organizada. En esta etapa se analizan los requisitos funcionales, los atributos de calidad, los stakeholders, las restricciones del proyecto y las principales preocupaciones arquitectónicas que influirán en las decisiones de diseño.

Esta revisión permite que la arquitectura se construya en función de los drivers más importantes del sistema, garantizando que las decisiones adoptadas respondan tanto a los requerimientos funcionales como a los atributos de calidad priorizados.

---

## Funcionalidad primaria del sistema

DriveShare es una plataforma colaborativa de alquiler de vehículos que conecta propietarios con usuarios interesados en alquilar un automóvil de forma segura, permitiendo administrar todo el ciclo de vida del alquiler, desde el registro del usuario hasta la calificación final de la experiencia.

Las funcionalidades principales identificadas son las siguientes:

| Módulo | Funcionalidad primaria |
|---------|------------------------|
| **Usuarios** | Gestionar el registro, autenticación, recuperación de contraseña, perfiles y control de acceso mediante roles y autenticación OAuth. |
| **Catálogo de Vehículos** | Registrar, editar, eliminar, publicar y consultar vehículos disponibles, incluyendo imágenes, disponibilidad y filtros de búsqueda. |
| **Reservas** | Gestionar el ciclo completo de las reservas, incluyendo disponibilidad, creación, modificación, cancelación y cierre del alquiler. |
| **Pagos** | Procesar pagos seguros, retener fondos, liberar pagos al propietario, gestionar reembolsos y registrar transacciones financieras. |
| **Reseñas y Reputación** | Permitir registrar calificaciones y comentarios asociados a reservas finalizadas para construir la reputación de propietarios y arrendatarios. |

---

## Stakeholders identificados

Los principales interesados considerados durante el diseño arquitectónico son:

| Stakeholder | Interés principal |
|--------------|------------------|
| **Arrendador** | Publicar vehículos, administrar disponibilidad, gestionar reservas y recibir pagos. |
| **Arrendatario** | Buscar vehículos, realizar reservas, efectuar pagos y dejar reseñas después del alquiler. |
| **Administrador** | Supervisar el funcionamiento general de la plataforma, administrar incidencias y controlar el correcto funcionamiento del sistema. |
| **Equipo de Desarrollo** | Diseñar una arquitectura modular, mantenible y escalable que facilite futuras mejoras. |
| **Equipo de Soporte** | Monitorear la plataforma, diagnosticar errores y garantizar la disponibilidad del servicio. |

---

## Atributos de calidad relevantes

Los atributos de calidad priorizados para DriveShare son:

| Atributo | Justificación |
|----------|---------------|
| **Seguridad** | La plataforma debe proteger la información personal, credenciales, pagos y reservas mediante mecanismos de autenticación y autorización. |
| **Disponibilidad** | Los usuarios deben poder consultar vehículos, realizar reservas y efectuar pagos de manera continua. |
| **Rendimiento** | Las búsquedas del catálogo y las consultas frecuentes deben responder en tiempos adecuados incluso con múltiples usuarios concurrentes. |
| **Integridad** | La información de vehículos, reservas, pagos y reseñas debe mantenerse consistente durante todo el proceso de alquiler. |
| **Mantenibilidad** | La arquitectura debe facilitar la incorporación de nuevas funcionalidades sin afectar el resto del sistema. |
| **Escalabilidad** | La plataforma debe soportar el crecimiento progresivo del número de usuarios, vehículos y reservas. |
| **Modificabilidad** | Debe ser posible reemplazar componentes o incorporar nuevos servicios con un impacto mínimo sobre la arquitectura existente. |

---

## Restricciones identificadas

Durante el análisis se identificaron las siguientes restricciones técnicas y de proyecto:

| Restricción | Descripción |
|--------------|------------|
| **Arquitectura Web** | DriveShare se implementa como una aplicación web basada en una arquitectura Cliente-Servidor. |
| **API REST** | La comunicación entre el frontend y el backend se realiza mediante servicios REST. |
| **Base de datos centralizada** | La información principal del sistema se almacena en un repositorio compartido para garantizar consistencia. |
| **Componentes especializados** | La arquitectura incorpora componentes como Storage Component, Cache Component, Database y Search Database para soportar diferentes funcionalidades. |
| **Desarrollo modular** | Cada integrante desarrolla un módulo independiente manteniendo coherencia con la arquitectura general. |
| **Tiempo del proyecto** | Las decisiones arquitectónicas deben ajustarse al alcance académico del curso. |

---

## Preocupaciones arquitectónicas

### Preocupaciones generales

| Preocupación | Descripción |
|--------------|------------|
| **Organización modular** | Cada módulo debe mantener responsabilidades claramente definidas. |
| **Separación de responsabilidades** | La arquitectura debe separar la presentación, lógica de negocio y persistencia. |
| **Comunicación entre módulos** | La interacción debe realizarse mediante interfaces bien definidas y desacopladas. |
| **Persistencia de información** | Los datos deben mantenerse consistentes y disponibles para todos los módulos. |
| **Evolución del sistema** | La arquitectura debe facilitar futuras ampliaciones sin requerir un rediseño completo. |

### Preocupaciones específicas

| Preocupación | Descripción |
|--------------|------------|
| **Autenticación y autorización** | Solo usuarios autenticados podrán acceder a funcionalidades protegidas según su rol. |
| **Gestión de disponibilidad** | Debe evitarse la reserva simultánea de un mismo vehículo para el mismo período. |
| **Procesamiento de pagos** | Las transacciones financieras deben realizarse de manera segura y confiable. |
| **Gestión de imágenes** | El almacenamiento de fotografías de los vehículos debe mantenerse desacoplado del módulo de negocio. |
| **Consistencia de reservas** | Los cambios en reservas deben reflejarse inmediatamente en la disponibilidad del catálogo. |
| **Reputación confiable** | Solo podrán registrarse reseñas asociadas a reservas finalizadas correctamente. |

---

## Drivers de arquitectura priorizados

A partir de la revisión de entradas se identifican los siguientes drivers arquitectónicos:

| Driver | Descripción | Prioridad |
|---------|-------------|-----------|
| **Seguridad** | Proteger usuarios, pagos y datos personales mediante autenticación y autorización. | Alta |
| **Integridad de la información** | Mantener consistencia entre vehículos, reservas, pagos y reseñas. | Alta |
| **Disponibilidad** | Garantizar que la plataforma permanezca operativa durante las operaciones críticas. | Alta |
| **Mantenibilidad** | Permitir la evolución independiente de cada módulo del sistema. | Alta |
| **Rendimiento** | Optimizar búsquedas, consultas y procesamiento de reservas. | Media |
| **Escalabilidad** | Soportar el crecimiento progresivo de usuarios y vehículos registrados. | Media |
| **Modificabilidad** | Facilitar la incorporación de nuevas funcionalidades y servicios. | Media |

---

## Revisión por módulo

| Módulo | Entradas principales revisadas | Riesgo arquitectónico |
|---------|-------------------------------|-----------------------|
| **Usuarios** | Registro, autenticación, OAuth, gestión de perfiles y recuperación de contraseña. | Alto |
| **Catálogo de Vehículos** | Registro, edición, disponibilidad, imágenes, filtros y consultas del catálogo. | Alto |
| **Reservas** | Disponibilidad, creación, modificación, cancelación y cierre de reservas. | Alto |
| **Pagos** | Procesamiento de pagos, reembolsos, retención de fondos y comprobantes. | Alto |
| **Reseñas y Reputación** | Registro de comentarios, calificaciones y reputación asociada a reservas finalizadas. | Medio |

---

## Conclusión de la revisión

La revisión de entradas confirma que **DriveShare** requiere una arquitectura modular, organizada mediante patrones arquitectónicos que favorezcan la separación de responsabilidades, la comunicación controlada entre componentes y la distribución adecuada de las funcionalidades del sistema.

Los principales drivers identificados —**seguridad, integridad, disponibilidad, mantenibilidad y rendimiento**— constituyen la base para las decisiones arquitectónicas que se desarrollarán en las siguientes iteraciones del método **Attribute-Driven Design (ADD)**.

Asimismo, la división del sistema en cinco módulos funcionales (Usuarios, Catálogo de Vehículos, Reservas, Pagos y Reseñas) permite que cada componente evolucione de manera independiente, manteniendo la coherencia, escalabilidad y mantenibilidad de la plataforma.
