# 11.1. Catálogo de Aplicaciones Actualizado

Esta sección actualiza el catálogo de aplicaciones presentado en **7.1**, materializando la arquitectura propuesta mediante la implementación del proyecto **DriveShare**. La estructura inicialmente definida durante la etapa de diseño se encuentra ahora implementada como código funcional, organizado en aplicaciones independientes y servicios desacoplados que pueden ser desplegados mediante contenedores Docker.

La implementación mantiene la separación entre la capa de presentación, la lógica de negocio, la auditoría, los microservicios y la infraestructura de soporte, siguiendo las decisiones arquitectónicas documentadas en el capítulo **8** y el diagrama de contenedores desarrollado en **10.2**. Cada contenedor definido en el modelo C4 puede asociarse directamente con una aplicación o servicio existente dentro del repositorio oficial del proyecto.

# Integración de decisiones arquitectónicas

Las decisiones arquitectónicas definidas durante la etapa de diseño fueron implementadas directamente dentro del código fuente del proyecto, garantizando la correspondencia entre la arquitectura propuesta, los patrones seleccionados y el prototipo funcional desarrollado.

| Decisión arquitectónica | Implementación en el proyecto |
|--------------------------|-------------------------------|
| **Arquitectura en Capas** | El Backend organiza la lógica del sistema mediante **Routes → Controllers → Services → Repositories → Models**, favoreciendo la separación de responsabilidades, la mantenibilidad y la reutilización del código. |
| **Cliente–Servidor** | El Frontend desarrollado en React consume los servicios REST implementados por el Backend mediante solicitudes HTTP y respuestas en formato JSON. |
| **Datos Compartidos** | Los servicios del proyecto utilizan mecanismos de persistencia desacoplados sobre sus respectivas bases de datos, empleando ORM y el patrón Repository para garantizar la consistencia e integridad de la información. |
| **Repository Pattern** | La persistencia de datos se implementa mediante repositorios especializados en cada servicio, desacoplando el acceso a la base de datos de la lógica de negocio. Tanto **DriveShare-Backend** como **DriveShare-Audit** implementan repositorios propios para gestionar la información correspondiente a cada dominio. |
| **Multi-Tier** | El sistema mantiene una separación física y lógica entre Frontend, Backend, Base de Datos, Sidecar de Auditoría, Microservicio de Pagos y servicios de infraestructura. |
| **Arquitectura Orientada a Servicios (SOA)** | El sistema integra servicios externos como Google OAuth, Resend y HashiCorp Vault, además de comunicarse con el Microservicio de Pagos como un servicio independiente, manteniendo desacoplada la lógica del dominio respecto a dichos componentes. |
| **Sidecar** | La auditoría del sistema se implementa mediante un servicio independiente (**DriveShare-Audit**) que registra automáticamente los eventos críticos generados por el Backend sin afectar su lógica de negocio. |
| **Gestión de Secretos** | HashiCorp Vault centraliza el almacenamiento seguro de las llaves RSA y demás secretos utilizados por la aplicación. |
| **Autenticación Híbrida** | El sistema implementa autenticación mediante credenciales propias y Google OAuth 2.0, utilizando JWT para la gestión de sesiones seguras. |
| **Rate Limiting** | Los endpoints críticos del Backend se encuentran protegidos mediante Express Rate Limit para mitigar ataques de fuerza bruta y abuso del servicio. |

Estas decisiones arquitectónicas permiten mantener una solución modular, segura, escalable y mantenible, garantizando la separación de responsabilidades entre los distintos componentes implementados y facilitando la evolución futura del proyecto conforme se incorporen nuevos módulos y funcionalidades.

# Arranque del entorno

El proyecto **DriveShare** fue diseñado para que todo el entorno de desarrollo pueda iniciarse mediante un único comando utilizando **Docker Compose**, permitiendo desplegar las aplicaciones, servicios de infraestructura y dependencias necesarias para el funcionamiento del sistema.

```bash
# Clonar el repositorio
git clone https://github.com/ulima-arqsoft/arqui261-grupo7.git

# Ingresar al proyecto
cd codigo
cd Driveshare

# Levantar todo el entorno
docker compose up --build
```

Una vez iniciado el entorno estarán disponibles las aplicaciones y servicios que conforman la arquitectura del sistema.

| Servicio | Función |
|-----------|---------|

# Flujo mínimo verificable de extremo a extremo

El prototipo funcional permite validar completamente el flujo correspondiente al **Módulo 1 – Usuarios y Seguridad**.

El usuario accede a **DriveShare-Frontend** y completa el formulario de registro → **DriveShare-Backend** valida la información recibida y verifica que el correo electrónico no se encuentre registrado → el usuario es almacenado en **PostgreSQL** → el sistema envía automáticamente un correo de verificación mediante **Resend** → el usuario verifica su cuenta utilizando el código recibido → posteriormente inicia sesión mediante credenciales locales o **Google OAuth 2.0** → el Backend genera un **JWT** para gestionar la sesión autenticada → cuando la operación requiere información sensible, las llaves criptográficas son obtenidas desde **HashiCorp Vault** → finalmente, las operaciones críticas generan automáticamente un evento que es enviado al **DriveShare-Audit**, donde queda registrado para fines de auditoría y trazabilidad.

La correcta ejecución de este flujo puede verificarse desde la interfaz web, mediante las respuestas de la API REST y a través de los registros almacenados por el servicio **DriveShare-Audit**.
