# 4.1. Módulo 1 / Integrante 1 (ARONI)

## 4.1.1. ADR-01: Decisión del mecanismo de autenticación y gestión de sesión

### Título
Selección del mecanismo de autenticación y gestión de sesión de los usuarios.

### Contexto
El módulo debe identificar a viajeros, microoperadores y administradores mediante inicio de sesión, y ofrecer además la opción de ingresar con una cuenta de Google. Asimismo, los demás módulos (catálogo, descubrimiento, reservas, pagos) necesitan validar quién realiza cada solicitud, por lo que esta decisión impacta directamente en la seguridad, el rendimiento y la interoperabilidad del sistema.

### Alternativas
**Alternativa 1:** Sesiones en el servidor con cookies (stateful). El servidor almacena la sesión de cada usuario y entrega al cliente un identificador para reconocerlo en cada solicitud.

**Alternativa 2:** Tokens JWT (stateless). El servidor emite un token de acceso de corta duración y un token de refresco, y cualquier módulo puede validar la identidad verificando la firma del token sin consultar un almacén de sesiones.

**Alternativa 3:** Delegar la autenticación por completo a un proveedor externo (OAuth 2.0 / OpenID Connect con Google) como único método de inicio de sesión.

### Criterios de Elección
* Seguridad.
* Escalabilidad entre módulos.
* Compatibilidad con la aplicación móvil.
* Interoperabilidad.
* Independencia de servicios de terceros.

### Decisión
Se realiza la selección de la alternativa 2, complementada con Google OAuth como método opcional de inicio de sesión.

### Sustento
Los tokens JWT permiten que cada módulo valide la identidad y el rol del usuario sin consultar al módulo de usuarios en cada solicitud, lo que reduce el acoplamiento y la carga sobre este módulo en temporadas de alta demanda. Además, funcionan bien en aplicaciones móviles, donde el manejo de cookies es menos natural. Se descarta la alternativa 3 porque dejaría el acceso a la plataforma sujeto a la disponibilidad de un tercero; por eso Google se mantiene solo como opción adicional y el inicio de sesión con correo y contraseña sigue disponible.

## 4.1.2. ADR-02: Decisión del modelo de control de acceso

### Título
Selección del modelo de control de acceso por roles y permisos.

### Contexto
La plataforma maneja tres tipos de usuario con funcionalidades distintas: el viajero descubre y reserva experiencias, el microoperador gestiona su catálogo y reservas, y el administrador modera cuentas y experiencias. El otorgamiento de roles tiene un fuerte impacto en quién puede crear, editar y publicar actividades, por lo que se requiere un modelo claro para restringir el acceso.

### Alternativas
**Alternativa 1:** Listas de control de acceso (ACL). Se asignan permisos de manera individual a cada usuario sobre cada recurso.

**Alternativa 2:** Control de acceso basado en roles (RBAC). Los permisos se asocian a roles (viajero, microoperador, administrador) y cada usuario recibe uno o más roles.

**Alternativa 3:** Control de acceso basado en atributos (ABAC). Las decisiones de acceso se evalúan según atributos del usuario, del recurso y del contexto mediante políticas.

### Criterios de Elección
* Simplicidad de implementación.
* Facilidad de mantenimiento.
* Granularidad del control.
* Facilidad de auditoría.

### Decisión
Se realiza la selección de la alternativa 2.

### Sustento
RBAC se ajusta a la estructura de la plataforma, que cuenta con tres roles bien definidos. El rol puede incluirse en el token de sesión para que los demás módulos lo consulten, y asignar o modificar el rol de un usuario es una operación simple para el administrador. ABAC ofrece más granularidad, pero su complejidad de configuración no se justifica para esta etapa, y las ACL por usuario se vuelven difíciles de mantener a medida que crece la cantidad de viajeros y operadores.

## 4.1.3. ADR-03: Modelo de Datos

### Título
Selección del modelo de datos para usuarios y perfiles.

### Contexto
Los usuarios y sus perfiles son una entidad referenciada por casi todos los módulos del sistema: el operador es dueño de un catálogo, el viajero realiza reservas y pagos, y el administrador modera cuentas. Por ello, el modelo de datos elegido debe garantizar la integridad de la información y las relaciones con los demás módulos.

### Alternativas
**Alternativa 1:** Modelo Relacional normalizado. Se separan las tablas de usuario, rol, perfil de viajero y perfil de microoperador, relacionadas mediante claves foráneas.

**Alternativa 2:** Modelo orientado a documentos. Cada usuario se almacena como un documento que contiene su información de perfil embebida, en formatos como JSON o BSON.

**Alternativa 3:** Modelo Relacional con columnas JSON. Se mantiene la tabla de usuarios relacional, pero los atributos del perfil se guardan en un campo JSON flexible.

### Criterios de Elección
* Integridad referencial con los demás módulos.
* Cumplimiento de los principios ACID.
* Normalización de los datos.
* Facilidad de consulta y de validación de datos.

### Decisión
Se realiza la selección de la alternativa 1.

### Sustento
El modelo relacional garantiza la integridad referencial entre usuarios, catálogos, reservas y pagos, y asegura que operaciones críticas como el registro y la asignación de roles se realicen de forma consistente. Además, al diferenciar el perfil de viajero y el de microoperador en tablas separadas, se mantienen campos obligatorios y validaciones específicas para cada tipo de usuario, algo que un esquema flexible (alternativas 2 y 3) haría más difícil de controlar.

## 4.1.4. ADR-04: Gestión de Credenciales

### Título
Selección del algoritmo de protección de contraseñas.

### Contexto
El módulo almacena las credenciales de los usuarios registrados con correo y contraseña. Una filtración de la base de datos no debe permitir recuperar las contraseñas originales, por lo que se requiere un mecanismo de protección adecuado, que además resista intentos de fuerza bruta.

### Alternativas
**Alternativa 1:** Función hash rápida con sal (por ejemplo, SHA-256 con sal). Es sencilla de implementar y muy rápida de calcular.

**Alternativa 2:** bcrypt. Función de hash diseñada para contraseñas, con un factor de costo configurable que vuelve más lento cada intento de adivinar una contraseña.

**Alternativa 3:** Argon2id. Función de hash de contraseñas moderna, resistente a ataques con hardware especializado gracias a su uso configurable de memoria.

### Criterios de Elección
* Resistencia a ataques de fuerza bruta.
* Madurez y soporte en el ecosistema Node.js.
* Rendimiento aceptable durante el inicio de sesión.
* Facilidad de integración.

### Decisión
Se realiza la selección de la alternativa 2.

### Sustento
bcrypt ofrece una protección sólida frente a la fuerza bruta mediante un costo ajustable, y cuenta con librerías maduras y ampliamente probadas en el ecosistema de Node.js, lo que reduce la complejidad de integración. Las funciones hash rápidas se descartan por ser demasiado veloces de atacar. Argon2id es una opción válida y más reciente, pero bcrypt cubre las necesidades de seguridad del módulo con menor complejidad de adopción para el equipo.

## 4.1.5. ADR-05: Elección de tecnologías del Módulo de Usuarios, Autenticación y Perfiles

### Título
React Native + Express + PostgreSQL (Prisma) + Docker

### Contexto
Las tecnologías elegidas deben permitir implementar los requisitos funcionales y de calidad del módulo (registro, autenticación, perfiles y roles), de manera coherente con las decisiones de autenticación, control de acceso, modelo de datos y gestión de credenciales anteriores.

### Alternativas
**Alternativa 1:** React Native + Express + PostgreSQL (Prisma) + Docker.

**Alternativa 2:** React Native + Express + Supabase (con su servicio de autenticación) + Docker.

**Alternativa 3:** React Native + Python (Django) + PostgreSQL + Docker.

### Criterios de Elección
* Seguridad.
* Adaptabilidad.
* Baja complejidad de la arquitectura.
* Control sobre la lógica de autenticación.

### Decisión
Se realiza la selección de la alternativa 1.

### Sustento
Express ofrece una estructura ligera para implementar los endpoints de registro, inicio de sesión y gestión de perfiles, con librerías maduras para JWT y bcrypt. Prisma facilita el acceso tipado a PostgreSQL y respeta el modelo relacional definido en el ADR-03, mientras que Docker permite que todo el equipo trabaje en entornos consistentes. Se prefiere esta opción frente a delegar la autenticación a Supabase para mantener el control sobre la emisión de tokens y roles que los demás módulos necesitan validar.
