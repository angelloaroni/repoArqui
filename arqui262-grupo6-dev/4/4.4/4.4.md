# 4.4. Módulo 4 / Integrante 4 (LOVERA)

## Módulo 4: Descubrimiento, Recomendaciones y Reputación

## 4.4.1. ADR-01: Integración de catálogo y disponibilidad

### Título
Elección entre orquestación de consultas y replicación de datos.

### Contexto
Descubrimiento combina información relativamente estática del Catálogo con horarios y cupos de Disponibilidad y Reservas. Los módulos funcionales mantienen sus propios límites y no necesariamente se despliegan como microservicios.

### Alternativas
|Alternativa|Descripción|Ventajas|Desventajas|
|----------|-----------|---------|-----------|
|Orquestar consultas por interfaces|Consultar los módulos propietarios al construir los resultados|Datos actuales y propiedad clara de la información|Puede aumentar la latencia por llamadas dependientes|
|Replicar datos para lectura|Mantener copias locales de catálogo y disponibilidad|Consultas rápidas y menor dependencia durante la lectura|Requiere sincronización y puede mostrar datos desactualizados|

### Criterios de Elección
- Vigencia de horarios y cupos.
- Complejidad de sincronización.
- Respeto por la propiedad de datos de cada módulo.
- Latencia de búsqueda aceptable para el MVP.

### Decisión
Se selecciona la orquestación mediante interfaces de Catálogo y Disponibilidad. Descubrimiento combina sus respuestas, pero no modifica las fuentes originales ni confirma cupos por su cuenta.

### Sustento
La consulta directa evita mantener copias desactualizadas de los cupos y reduce la complejidad de sincronización durante el MVP. Si el volumen de consultas crece, se podrá evaluar una proyección de lectura con una política explícita de actualización.

## 4.4.2. ADR-02: Modelo de datos de reputación

### Título
Elección de un modelo relacional para reseñas y calificaciones.

### Contexto
Las reseñas deben asociarse a una experiencia y a un viajero que haya completado una reserva. También se requiere consultar el historial y calcular valoraciones promedio sin admitir calificaciones duplicadas para una misma reserva.

### Alternativas
|Alternativa|Descripción|Ventajas|Desventajas|
|----------|-----------|---------|-----------|
|Modelo relacional|Relacionar reseñas con usuarios, experiencias y reservas|Integridad referencial y consultas de agregación|Requiere definir relaciones y restricciones|
|Modelo documental|Guardar cada reseña como un documento flexible|Esquema flexible y lectura del documento completo|Mayor complejidad para validar relaciones y calcular agregados consistentes|

### Criterios de Elección
- Integridad entre reseña, usuario, experiencia y reserva.
- Prevención de reseñas duplicadas.
- Facilidad para calcular promedios e historial.
- Coherencia con la persistencia elegida por el proyecto.

### Decisión
Se selecciona el modelo relacional, con una restricción que permita como máximo una reseña por reserva completada.

### Sustento
Las relaciones y restricciones permiten verificar la elegibilidad de una reseña y mantener los promedios consistentes. La decisión se alinea con el uso de Supabase y PostgreSQL definido para el Catálogo.

## 4.4.3. ADR-03: Estrategia de recomendaciones

### Título
Elección entre reglas explícitas y personalización por comportamiento.

### Contexto
El MVP debe sugerir y ordenar experiencias con información ya disponible, sin asumir mecanismos de tracking o personalización por comportamiento del usuario. Categorías y valoraciones ofrecen criterios iniciales verificables.

### Alternativas
|Alternativa|Descripción|Ventajas|Desventajas|
|----------|-----------|---------|-----------|
|Reglas explícitas|Ordenar por categorías seleccionadas y valoración promedio, considerando filtros de búsqueda|Explicable, sencillo de probar y de bajo costo|Menos personalizado para cada viajero|
|Personalización por comportamiento|Registrar interacciones y generar recomendaciones individuales|Puede aumentar la relevancia con suficientes datos|Mayor complejidad, requiere datos y plantea consideraciones de privacidad|

### Criterios de Elección
- Alcance inicial del proyecto.
- Explicabilidad de los resultados.
- Privacidad y minimización de datos.
- Complejidad de implementación y validación.

### Decisión
Se eligen reglas explícitas basadas en categorías y valoración promedio. No se incorpora seguimiento del comportamiento en el MVP.

### Sustento
Las reglas son simples de explicar, probar y ajustar con los datos previstos por el proyecto. Evitar tracking reduce complejidad y recolección de datos personales mientras se valida el valor de las recomendaciones.

## 4.4.4. ADR-04: Gestión de rendimiento de búsquedas

### Título
Elección de caché del servidor para consultas frecuentes.

### Contexto
Las consultas de descubrimiento pueden combinar filtros de catálogo, reputación y disponibilidad. El volumen de lecturas puede crecer durante temporadas turísticas y elevar la latencia si cada búsqueda repite consultas costosas.

### Alternativas
|Alternativa|Descripción|Ventajas|Desventajas|
|----------|-----------|---------|-----------|
|Caché del lado del servidor|Conservar temporalmente resultados frecuentes con expiración o invalidación|Reduce consultas repetidas y carga del servidor|Debe definirse cómo expiran o se invalidan los datos|
|Sin caché|Consultar las fuentes de datos en cada solicitud|Evita complejidad de invalidación|Aumenta la carga y el tiempo de respuesta con el crecimiento del catálogo|

### Criterios de Elección
- Velocidad de búsqueda.
- Vigencia de la información de disponibilidad.
- Reducción de carga en consultas repetidas.
- Facilidad para configurar la expiración.

### Decisión
Se selecciona caché del lado del servidor para resultados frecuentes de catálogo y reputación, junto con paginación e índices de búsqueda. Los cupos se verifican con el módulo propietario y no se presentan como confirmados a partir de datos expirados.

### Sustento
El caché reduce la repetición de consultas sin sacrificar la vigencia de los cupos. La expiración e invalidación de catálogo y valoraciones permiten controlar la frescura de los resultados.

## 4.4.5. ADR-05: Tecnologías del módulo

### Título
Selección de tecnologías para Descubrimiento, Recomendaciones y Reputación.

### Contexto
El módulo debe ofrecer búsquedas, filtros y recomendaciones, consultar catálogo y disponibilidad, y gestionar reseñas. La elección debe ser coherente con las tecnologías registradas para el módulo de Catálogo y Gestión de Experiencias.

### Alternativas
1. **React Native + Express + PostgreSQL + Docker.**
2. **React Native + Python + PostgreSQL + Docker.**
3. **React Native + Express + Supabase + Docker.**

### Criterios de Elección
- Compatibilidad con la aplicación móvil.
- Rendimiento en consultas de lectura.
- Adaptabilidad y facilidad de mantenimiento.
- Baja complejidad de arquitectura para el MVP.

### Decisión
Se selecciona React Native + Express + Supabase + Docker, en concordancia con la decisión tecnológica documentada para el módulo de Catálogo.

### Sustento
La reutilización del stack del Catálogo reduce la complejidad de integración y permite consultar los datos de experiencias con tecnologías conocidas por el equipo. Las interfaces entre módulos mantienen separadas sus responsabilidades y permiten evolucionar la solución según las necesidades de escala.
